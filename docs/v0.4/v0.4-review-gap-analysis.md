# TraceMotive v0.4 review gap analysis

Status: final design input. This document does not change the package version,
the Frozen v0.1 contract, or release state.

## 1. Method and evidence boundary

The checkout was reviewed as it exists at the start of this design cycle. The
source request contains the A-L review themes from Claude, Grok, and Manus, but
the checkout does not contain those three reports or any file naming those
reviewers. The A-L themes below are therefore treated as the review corpus. No
reviewer-specific quotation, score, or conclusion is invented.

The following repository evidence was used:

- `spec/v0.1-frozen-spec.md` remains the highest-authority compatibility
  contract. `spec/v0.2-proposed-spec.md` and `spec/v0.3-proposed-spec.md` are
  historical proposed specifications, not authority to rewrite v0.1.
- The runtime path is already Framework -> adapter -> Canonical -> bounded
  transport -> Collector -> SQLite -> Query API -> UI.
- `tracemotive/comparison.py` already has deterministic structural comparison,
  JSON Pointer paths, ambiguity barriers, capture-state handling, and global
  comparison bounds. v0.4 should expose and explain that evidence rather than
  replace it with heuristic pairing.
- `tracemotive/divergence.py`, `findings.py`, and `investigation.py` already
  separate supported observations, uncertainty barriers, context-only signals,
  primary findings, additional findings, and last reliable matches.
- `tracemotive/api_v3.py` is additive and intentionally compact; v0.4 must not
  silently alter its response or the v1/v2 routes.
- `frontend/src/trace-list.tsx`, `trace-comparison.tsx`,
  `comparison-insight.tsx`, `trace-detail.tsx`, `app.tsx`, and `api.ts` show the
  current UI gaps described below.
- `.github/workflows/ci.yml` builds the frontend package before Python tests,
  while ignored generated assets are absent from a fresh git checkout. This is
  why the current CI path can pass while a fresh checkout cannot serve the UI.
- `docs/divergence-evaluation-v0.3.md` is corpus-specific. Its required public
  facts are 30 mandatory scenarios, 15 expected confident meaningful cases, 14
  supported investigation starting points, false-confident meaningful
  target/result 0, and false-confident starting-point target/result 0.

## 3. Gaps by review theme

### A. Ecosystem position and interoperability

Current state:

- Only the OpenAI Agents adapter is implemented and public support is described
  as `>=0.17,<0.18`; the repository documents tested checkpoints but does not
  prove every patch release in that range.
- There is no LangGraph adapter, runtime fixture, or integration test in the
  checkout. The v0.3 proposed specification only made LangGraph conditional.
- There is no OpenTelemetry exporter, span-link contract, or distributed trace
  model, which is consistent with the Frozen exclusions.

v0.4 decision:

- OpenAI Agents remains the validated adapter. LangGraph is Conditional v0.4,
  not unconditional P0: it requires a full GO gate covering a real public
  runtime fixture, lifecycle mapping, privacy/security tests, failure isolation,
  installed smoke, exact version wording, and maintainer dogfood. If any GO
  condition fails, defer it to v0.4.1 and remove the v0.4 support claim.
- Keep the adapter boundary Canonical. Framework objects, callback objects,
  graph state objects, and provider objects stop at the adapter.
- Keep OTel interoperability at a safe boundary: document field-level mapping
  guidance and reserve an additive future exporter. Do not add OTLP export,
  distributed tracing, span links, or a cloud dependency to v0.4.
- Do not widen the OpenAI support promise until the matrix is reproducible.

### B. Passive investigation versus an investigation cockpit

Current state:

- v3 supplies an investigation summary, but it does not provide explicit
  left-span, right-span, full-comparison, copy-evidence, or local
  comparison-reference actions.
- The trace detail view has a span tree and inspector, but no deep-linkable span
  route. Comparison selection is local component state and is not a visible
  persistent tray.
- v3 already has the correct evidence roles; the UI must reveal them without
  promoting the primary finding to a diagnosis.

v0.4 decision:

- Keep the cockpit minimal: `Look here`, `What changed`, `Evidence`, `Next`,
  and `What TraceMotive does not know`.
- The primary actions are only `Open left span`, `Open right span`, and `Full
  comparison`. Copy evidence/link is secondary and never calls a remote share
  service.
- Add stable hash routes for trace detail and span detail, plus a compact
  left/right selection control. Do not turn the screen into a dashboard.
- Keep “observed”, “uncertain”, “not observed”, and “not available” language.
  Do not add good/bad, root-cause, confidence, importance, or causal labels.

### C. Structure-aware JSON diff

Current state:

- v2 already recursively compares object keys and list positions with sorted
  deterministic paths. v0.4 needs a narrower operation contract: `add`,
  `remove`, and `replace`.
- v3 findings retain compact evidence but do not expose the requested bounded
  structured diff or the explicit capture/redaction no-diff rule.
- Arrays must not infer identity or moves. Complex arrays may fall back to one
  whole-array replacement rather than misleading element alignment.

v0.4 decision:

- Reuse the existing comparison engine and expose a conservative bounded
  projection. Emit no diff for capture-unavailable or redacted fields; retain
  the limitation/uncertainty reason instead.
- Sort object keys and JSON Pointer paths deterministically, bound depth/nodes/
  change records, preserve ambiguity barriers, and expose truncation as a fact.
  Never infer importance from path depth, field names, chronology, value size,
  or a score.
- Sanitize before persistence and before response composition. Render values as
  inert JSON/text; never use HTML injection, markdown execution, or dynamic
  component selection from captured data.

### D. Empty-state onboarding

Current state:

- The empty state says only `No traces recorded yet.` and offers no API-key-free
  demo command or actual-agent instrumentation route.
- `tracemotive demo` already seeds a deterministic local pair without an API
  key, but the UI does not teach that path.

v0.4 decision:

- Add copyable, visible commands for the deterministic demo and the actual
  OpenAI Agents integration. The actual-agent path must state that an API key is
  only required by the user's agent, not by TraceMotive itself.
- The browser only copies text or changes local routes. It never executes shell
  commands, probes API keys, or sends content externally.

### E. Fresh-checkout packaging failure

Current state:

- `scripts/package_frontend.py` correctly copies built assets, but the generated
  destination is ignored and not present in a fresh clone.
- The README's fresh-checkout path does not run `npm ci` and
  `npm run build:package`.
- `tests/test_packaging.py` copies the working tree, including ignored generated
  assets, so it is not equivalent to a fresh git checkout.
- CI runs the build before tests, masking this bootstrap gap.

v0.4 decision:

- Add one cross-platform, dependency-light repository bootstrap command that
  runs the frontend install/build/package sequence and returns actionable
  errors. Use it in README, CONTRIBUTING, CI, and fresh-checkout E2E.
- Add a tracked-file-only or `git archive` E2E that proves install -> bootstrap
  -> package -> serve -> demo seed -> Query API -> packaged UI, without Node or
  the checkout after wheel installation.
- Make the packaging test fail if it accidentally relies on ignored generated
  assets.

### F. Trace selection and metadata

Current state:

- The list has per-row left/right buttons and a wide table, but no compact
  left/right selection control or durable URL state.
- The current query list intentionally returns summary fields, not arbitrary
  Canonical metadata or attributes; v0.4 should preserve that boundary.

v0.4 decision:

- Add a compact visible left/right selection control, deterministic filters,
  clear actions, and URL restoration after comparison starts.
- Do not expand the list into an arbitrary metadata explorer. Do not pass
  captured content or arbitrary attributes through the list endpoint and do not
  change Canonical merely to improve a table.
- Use neutral labels such as “observed difference” and “trace status”; never
  label a trace good/bad or rank it by inferred quality.

### G. API-key-free demo coverage

Current state:

- There is one deterministic demo pair and a strong v3 scenario/evaluation
  corpus, but no user-facing uncertain scenario.

v0.4 decision:

- Keep the existing default demo stable and add only two Core scenarios: an
  identified behavioral difference and an uncertainty barrier. A no-difference
  scenario/full catalog is optional if cheap and bounded; it must not delay the
  cockpit or diff.
- Each scenario uses realistic sanitized shapes, is local-only, repeatable, and
  has an exact expected investigation state.

### H. README first 30 seconds

Current state:

- The README already has a local-first message, a demo GIF, quick start, safety
  language, and explicit exclusions, but the first screen is not organized as a
  problem -> example -> five-minute trial path.
- The current promise is evidence-oriented, but v0.4 must guard against any
  wording that implies causality.

v0.4 decision:

- Reorder the opening: problem, screenshot/GIF, API-key-free trial, supported
  integrations, privacy/safety, evaluated scope, limitations, and architecture.
- Use exact current v0.3 evaluation numbers only with corpus-specific labels.
- State what TraceMotive cannot establish. Remove hype, universal guarantees,
  and unverified framework claims.

### I. Evaluation transparency

Current state:

- The v0.3 evaluation document already exposes exact counts and says they are
  corpus-specific, but the landing documentation does not surface the result
  early enough.

v0.4 decision:

- Add a short README evaluation card linked to the full report and a reproducible
  command. State exactly: 30 mandatory scenarios, 15 expected confident
  meaningful cases, 14 supported investigation starting points, false-confident
  meaningful target/result 0, and false-confident starting-point target/result 0.
  Include scenario/corpus version.
- Do not convert the report into a product-wide accuracy or confidence claim.

### I. Maintainer dogfood validation

The current automated corpus is not a substitute for a small realistic agent
failure run. v0.4 adds a local maintainer dogfood gate with exact expected
outcomes:

- repeated-tool count `2 -> 3` on a complete trace is a supported group-level
  cardinality change;
- equal-count repeated members with unsafe identity or reordering are uncertain.

“Uncertain or group count only” is not an acceptable combined criterion. This is
local maintainer validation, not external user validation.

### J. Version, specification, and history consistency

Current state:

- Package version is 0.3.0, while v0.1 is Frozen and v0.2/v0.3 are proposed
  documents. That distinction is correct but easy to lose in new prose.

v0.4 decision:

- Keep these files as the frozen v0.4 implementation design, separate from the
  production version/spec acceptance that will happen in a later authorized
  change.
- Preserve `schema_version: "0.1"`, ingest protocol `1`, and v1/v2/v3 API
  behavior. A package release number is not a Canonical schema version.
- Add a version matrix to README/release notes rather than mechanically
  replacing historical version strings.
- Add `/api/v4` because the new bounded operation diff, no-diff capture
  semantics, conservative array fallback, and cockpit actions cannot be
  composed into the unchanged v3 contract. This is a response-contract decision,
  not package-version-driven API versioning.

### K. PyPI and maintainer trust

Current state:

- `pyproject.toml` has MIT licensing and contributor copyright text but lacks
  maintainer identity, project URLs, and a provenance policy.
- A live PyPI lookup during this review did not find a `tracemotive` project
  page. No public maintainer identity should be invented from that absence.

v0.4 decision:

- Before publication, require project-level ownership, verified project URLs,
  license metadata, source/wheel reproducibility evidence, release provenance,
  security contact, and a documented maintainer identity strategy.
- Keep identity statements at organization/project level unless a real owner
  authorizes personal attribution. Publication is a separate authorization from
  this design.

### L. Release cadence

v0.4 is release-ready only when the quality gate passes. A date, review score, or
completed implementation issue cannot override a failed fresh-checkout, privacy,
runtime, or packaging gate.

## 4. Highest-risk gaps

1. Fresh-checkout packaging is the immediate P0 because it invalidates the
   documented first-run path.
2. A new investigation UI can accidentally imply diagnosis if evidence roles,
   uncertainty, and navigation targets are not explicit.
3. Exposing JSON values creates a privacy/XSS/DoS surface even when the diff
   algorithm is deterministic.
4. LangGraph support is a credibility risk if declared without a real public
   runtime matrix.
5. A package identity or PyPI claim without verified ownership is a maintainer
   trust risk.

## 5. Acceptance interpretation

The review goal is not “add every requested feature.” It is to make at least 90%
of actionable criticism have a concrete implementation, test, or explicit
defer/reject decision. The scorecard in
`docs/v0.4/v0.4-review-scorecard.md` counts each review unit once, records the
decision, and distinguishes material implementation from justified deferral.

# TraceMotive v0.4 Frozen Specification

Status: frozen for v0.4 implementation planning. This document is not yet
applied to production; `spec/v0.1-frozen-spec.md` remains the repository's
highest authority for the current implementation.

## 1. Authority and compatibility

1. The v0.1 Frozen Specification remains unchanged and authoritative for
   Canonical schema, lifecycle, privacy, transport, loopback, and framework
   boundaries.
2. v0.4 is additive. It preserves Canonical `schema_version: "0.1"`, ingest
   protocol `1`, HTTP collector v1, and the existing v1/v2/v3 Query API
   contracts.
3. A distribution version such as `0.4.0` must never be substituted for a
   schema or protocol version.
4. v0.4 may add a v4 Query API and UI behavior. It must not require v3 clients
   to parse v4 data.

The keywords MUST, MUST NOT, SHOULD, and MAY are normative in this document.

## 2. Product contract

TraceMotive v0.4 MUST present observed execution evidence and investigation
limitations. It MUST NOT claim RCA, causality, importance, confidence,
replayability, or a good/bad judgment from the data described here.

An observation is “confirmed” only when the existing structural alignment and
capture rules support it. A barrier MUST remain “uncertain”, “unavailable”, or
another existing non-confident state. Equal redaction placeholders MUST NOT be
treated as equal source values.

## 3. API version decision and comparison endpoint

The package version MUST NOT by itself cause an API version bump. The server
MUST keep `/api/v3/compare/{left}/{right}` unchanged.

The design decision is that unchanged v3 plus the existing detail route cannot
provide the new operation-based bounded diff, explicit capture/redaction
no-diff behavior, conservative array fallback, and cockpit action targets
without changing an existing contract. Therefore v0.4 adds:

```text
GET /api/v4/compare/{left_trace_id}/{right_trace_id}
```

The endpoint MUST:

- accept only valid trace identifiers;
- use one read-only snapshot per trace for one response;
- use existing v2 structural comparison and v3 investigation semantics;
- return `comparison_version: "0.4"`;
- preserve deterministic ordering and exact JSON numbers;
- return a bounded response no larger than the existing response-size limit;
- reject or explicitly mark unavailable malformed, missing, oversized, or
  structurally invalid data; and
- avoid all writes, network calls, framework imports, and LLM calls.

The endpoint MUST NOT change the semantics or byte shape of `/api/v1`,
`/api/v2/compare`, or `/api/v3/compare`. This is the exact justification for
v4: it protects the existing v3 response contract while introducing a response
contract that is materially different, not merely a package-version label.

## 4. Structured diff contract

Each v4 finding MAY contain `structured_diff` and MUST contain
`structured_diff_truncated` when the field is present.

An entry has this shape:

```json
{
  "op": "replace",
  "path": "/json/pointer/with~1escaped~0tokens",
  "left": {"state": "present", "value": null},
  "right": {"state": "present", "value": {"safe": true}},
  "reason": null
}
```

Allowed values:

- Entry `op`: `add`, `remove`, `replace`.
- Observation `state`: `present`, `absent`, `unavailable`, `redacted`.
- `reason`: an existing stable comparison/privacy/alignment reason code or JSON
  `null`; no free-form provider error or raw value.

Rules:

1. JSON Pointer escaping MUST follow RFC 6901 semantics already used by the
   comparison engine: `~` becomes `~0` and `/` becomes `~1`.
2. A present JSON `null` MUST use a `present` wrapper with `value: null`.
3. An absent side MUST use `absent` and MUST NOT use a bare JSON `null` as a
   substitute.
4. If capture is unavailable or redacted on either side of a field, no diff
   entry MUST be emitted for that field. The response MUST retain an explicit
   limitation/uncertainty reason instead.
5. `unavailable` and `redacted` MUST NOT contain raw source content.
6. Values MUST already have passed the existing privacy sanitizer and Canonical
   normalization. They MUST remain inert JSON data.
7. Object keys and paths MUST be ordered deterministically. Scalar arrays MAY be
   compared by index only; an index is never an inferred identity.
8. Arrays MUST NOT infer identity or moves. Arrays containing objects or nested/
   heterogeneous values MUST use a bounded whole-array `replace` fallback when
   element alignment could mislead. If the whole array cannot fit the bounds,
   no values are emitted and truncation is reported.
9. Repeated groups with ambiguous identity MUST remain unavailable and MUST NOT
   receive a member-level navigation action.
10. The implementation MUST bound maximum diff depth at 32, visited diff nodes at
    4096, and change records at 256 per finding, in addition to the existing
    aggregate response-size limit. These are projection limits, not Canonical
    schema limits.
11. The response MUST expose truncation and its stable reason whenever a bound
    is reached.
12. The implementation MUST be recursion-safe and bounded for hostile depth,
   breadth, strings, and total bytes.
13. No importance, confidence, causal, or diagnosis field may be derived from
    the diff.

The per-finding cap is an implementation constant tested as part of the v4
contract. It MUST be no larger than the existing aggregate difference-record
and response-size limits.

## 5. Action contract

Actions are optional records of the form:

```json
{
  "type": "open_left",
  "target": {"trace_id": "...", "span_id": "..."}
}
```

Allowed action types are:

- `open_left`;
- `open_right`;
- `full_comparison`;
- `copy_evidence`; and
- `copy_local_reference`.

Action rules:

- A target MUST be unique and validated. Missing or ambiguous targets MUST
  result in omission, not a guessed target.
- `open_left`, `open_right`, and `full_comparison` MUST resolve to local hash
  routes only.
- `copy_evidence` MUST identify a finding and cause the UI to copy only the
  sanitized v4 evidence already visible in the response.
- `copy_local_reference` MUST copy a hash-only local comparison route. It MUST
  NOT create a public share link, upload data, or include credentials.
- The browser MUST show a text fallback when clipboard permission is denied.

The route forms are:

```text
#/traces/{trace_id}
#/traces/{trace_id}/spans/{span_id}
#/compare/{left_trace_id}/{right_trace_id}
```

The UI MUST validate route segments and MUST render captured values as inert
JSON/text. A deleted target MUST produce an explicit not-found view.

## 6. Minimal cockpit and UI contract

The comparison cockpit MUST remain minimal and MUST provide only these named
sections:

1. `Look here`;
2. `What changed`;
3. `Evidence`;
4. `Next`; and
5. `What TraceMotive does not know`.

The primary actions MUST be exactly `Open left span`, `Open right span`, and
`Full comparison`. Copy evidence and copy local reference MAY remain secondary.
The cockpit MUST NOT become a dashboard, add inferred ranking, or add good/bad
labels.

The cockpit MUST provide a compact left/right selection control with clear
semantics and a deterministic way to restore a comparison after navigation.

When no traces exist, the UI MUST show:

- a copyable command for `tracemotive serve`;
- copyable commands for the deterministic identified and uncertain local demos;
- a copyable actual-agent instrumentation example; and
- a statement that TraceMotive itself does not require an API key for the local
  demo or collector.

The UI MUST NOT execute commands, probe environment variables for keys, send
captured content to a remote service, or interpret captured HTML/script.

## 7. Demos and evaluation

The default demo pair MUST remain deterministic and compatible with its current
documented behavior. v0.4 Core MUST add two small, API-key-free scenarios:

- an identified observed behavioral difference; and
- an uncertain comparison caused by an evidence/alignment barrier.

A none/identical scenario or a larger catalog MAY be added only if cheap and
bounded; demo breadth MUST NOT delay the cockpit or structured diff. Each
scenario MUST declare its expected state and limitations.

The README MUST surface the current evaluation facts only as corpus-scoped
evidence:

- 30 mandatory scenarios;
- 15 expected confident meaningful cases;
- 14 supported investigation starting points in the current corpus;
- false-confident meaningful target/result for a conforming engine: 0; and
- false-confident starting-point target/result for a conforming engine: 0.

If other state counts are shown, they MUST be derived from the same named corpus
and labeled. A future v0.4 result MUST use a new corpus/version label if the
corpus changes.

## 8. Maintainer dogfood

Before release, a local maintainer dogfood run MUST use realistic agent-failure
fixtures and assert exact outcomes:

- repeated-tool count `2 -> 3` on a complete trace MUST be a supported
  group-level cardinality change; and
- equal-count repeated members with unsafe identity or reordering MUST be
  uncertain.

The acceptance criterion MUST NOT say “uncertain or group count only”. This is
local maintainer validation, not external user validation or a market claim.

## 9. Integrations

OpenAI Agents MUST remain supported only through public APIs and the tested
compatibility matrix. The adapter MUST preserve capture-off defaults, pre-queue
redaction, and failure isolation.

LangGraph is Conditional v0.4 only if the named public runtime versions pass:

- real lifecycle capture;
- Canonical boundary tests;
- capture-off and redaction tests;
- malformed/oversized hostile input tests;
- no API-key probing by TraceMotive;
- installed-user smoke; and
- documentation matching the exact tested matrix.

The full GO gate also requires the repeated-tool dogfood outcomes above and the
complete release gate. If any GO condition does not pass, v0.4 MUST reject the
support claim and defer the adapter to v0.4.1.

OTel export, distributed tracing, and span links are deferred and MUST NOT be
implemented as hidden compatibility behavior.

## 10. Build and package contract

The repository MUST have one documented bootstrap command that runs the
frontend install, build, and package steps. README, CONTRIBUTING, CI, and the
fresh-checkout E2E MUST invoke that same entry point.

The release candidate MUST prove, from tracked files without ignored generated
assets:

```text
fresh checkout
 -> install dependencies
 -> bootstrap frontend package
 -> build artifact
 -> install artifact outside checkout
 -> serve loopback-only
 -> seed identified and uncertain local demos
 -> query v1/v2/v3/v4
 -> load packaged UI without Node or source checkout
```

The package MUST contain the UI assets required by `serve`. A missing asset
must fail with an actionable build/package error, never silently fall back to a
source checkout or memory-only server.

## 11. Security invariants

All v0.1 security invariants remain mandatory:

- disabled by default;
- content capture independently disabled by default;
- redaction before transport queue;
- no known credentials persisted;
- loopback-only HTTP collector;
- captured content untrusted and inert;
- no analytics or external telemetry; and
- tracing failures never fail agent execution.

v0.4 adds mandatory tests for hostile UI content, URL/clipboard handling,
encoded traversal, malformed and oversized JSON, deep JSON, ambiguous repeated
spans, SQLite restart behavior, dependency metadata, and adapter failure
isolation.

## 12. Release decision

The design is frozen for implementation planning. Production implementation
still requires the scope, API shape, test matrix, support claims, and release
gates to be applied in a separate authorized change. A release date cannot
override a failed gate. No publication, tag, push, or PyPI upload is implied.

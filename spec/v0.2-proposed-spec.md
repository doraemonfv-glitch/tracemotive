# TraceMotive v0.2 Proposed Specification

Status: Proposed
Specification version: 0.2-proposed
Target package version: 0.2.x
Canonical schema version: "0.1"
Ingest protocol version: 1
Existing Query API version: v1
Comparison Query API version: v2

---

## 0. Authority and interpretation

This document defines the proposed TraceMotive v0.2 contract. It is not a
Frozen specification.

`spec/v0.1-frozen-spec.md` remains historically frozen and MUST NOT be edited
as part of v0.2 work. For every behavior that already exists in v0.1, the
Frozen Specification remains the compatibility authority. This document adds
v0.2 behavior only where it explicitly says that the behavior is new or
additive.

The following precedence applies to v0.2 implementation work:

1. `spec/v0.1-frozen-spec.md` for existing v0.1 behavior.
2. This document for new v0.2 behavior.
3. `AGENTS.md` for repository implementation rules.
4. An implementation choice explicitly allowed by both specifications.

The terms MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative.

An implementation MUST NOT infer a missing public behavior from a framework's
private objects, an advisory review, or an apparent implementation
convenience. If this document does not define a required v0.2 behavior, the
implementation MUST stop at the nearest defined boundary and report the gap
instead of silently inventing a contract.

## 1. v0.2 objective and scope

TraceMotive v0.2 evolves the v0.1 local observation kernel into an actually
useful local debugger while preserving the v0.1 observation contract.

The v0.2 product provides:

* persistent local Collector storage;
* one-command local Collector and production UI startup;
* packaged production UI assets that do not require Node.js or npm for normal
  users;
* read-only comparison of two observed Traces;
* Simple Structural Alignment v1 and field-level observed differences;
* localized ambiguous groups and unavailable observations;
* regression and release gates for the above behavior.

### 1.1 Priority scope

P0 MUST include:

* persistent local SQLite;
* `tracemotive serve`;
* packaged production UI;
* trace comparison;
* Simple Structural Alignment v1;
* structural Span and Trace differences;
* localized ambiguity and unavailable-observation reporting;
* regression, packaging, privacy, and release gates.

P1 MAY include after all P0 gates pass:

* OpenAI Agents SDK compatibility matrix work;
* README and onboarding redesign;
* LangGraph feasibility evaluation;
* LangGraph adapter implementation only if the feasibility contract passes.

P2 is outside the v0.2 implementation commitment:

* CrewAI integration;
* other framework adapters.

The following MUST NOT be implemented as part of v0.2:

* Replay or recorded replay;
* automatic root-cause analysis;
* causal certainty or causal scoring;
* first observed difference;
* first divergence;
* causal ranking;
* root cause candidate;
* causal proof;
* causal evidence graph or causal edge APIs;
* failure responsibility attribution;
* cloud sync or hosted backend;
* remote Collector support;
* authentication, accounts, teams, or multi-user storage;
* persistent SDK offline spool;
* automatic retention, archival, or deletion tombstones;
* streaming token/chunk persistence;
* WebSockets or streaming UI updates;
* artifact/blob storage;
* OpenTelemetry/OTLP export;
* execution forking or intervention experiments;
* advanced search or query language;
* automatic model selection or model recommendation.
* unconditional heuristic matching as a P0 alignment behavior.

The first observed difference, first divergence, causal ranking, root cause
candidate, and causal proof are deferred research topics. They MUST NOT be
implemented in the v0.2 P0 comparison or release gate. Existing Issue #1
first-divergence exploration MAY later define a compatible extension, but it
is not a v0.2 P0 dependency.

The P0 value proposition is limited to:

1. local Traces survive Collector restart;
2. TraceMotive starts through a normal one-command local experience;
3. released production UI use does not require Node.js or npm;
4. users can compare two Agent runs;
5. users can quickly isolate and visually inspect observed differences;
6. Simple Structural Alignment v1 is validated against realistic Traces
   before its behavior is treated as production-ready.

### 1.2 Version identity

The package version and protocol/schema versions are separate identities.

* A v0.2 package MAY use package version `0.2.x`.
* Existing Canonical Trace and Span objects MUST continue to use
  `schema_version = "0.1"`.
* Existing ingest envelopes MUST continue to use `protocol_version = 1`.
* Existing `/api/v1` request and response contracts MUST remain unchanged.
* New comparison responses use `comparison_version = "0.2"` and the additive
  `/api/v2` namespace defined below.
* An upstream framework version MUST NOT define Canonical schema versioning.

## 2. Architectural invariants

All v0.1 invariants remain in force.

The v0.2 architecture is:

```text
Framework
  -> Integration Adapter
  -> Canonical Trace Events
  -> Bounded Local Transport
  -> Loopback Collector
  -> SQLite Backend
  -> Query API v1/v2
  -> UI
```

The following MUST remain true:

1. Framework objects stop at the Integration Adapter.
2. The Collector MUST remain framework-agnostic.
3. The Python SDK MUST NOT depend on SQLite or FastAPI.
4. The frontend MUST access data only through the Query API.
5. Canonical representation MUST remain framework-independent.
6. TraceMotive MUST remain disabled by default.
7. Content capture MUST remain independently disabled by default.
8. Redaction MUST occur before an event enters the SDK transport queue.
9. Only redacted, normalized Canonical data may reach the Repository.
10. Known API keys and credentials MUST NOT be persisted.
11. Captured content MUST remain untrusted data.
12. React MUST NOT execute captured HTML, script, or arbitrary code.
13. Tracing failures MUST NOT fail Agent execution.
14. The Collector and `tracemotive serve` MUST be loopback-only.
15. TraceMotive MUST make no analytics or external telemetry request.
16. v0.2 MUST NOT add a persistent SDK spool.
17. Existing v0.1 delete semantics MUST remain: no tombstone and later ingest
    MAY recreate deleted state.

The persistence boundary is the Collector Repository. A file-backed
Repository is not an SDK spool. If the Collector process is unavailable or
the SDK process exits with events still in the in-memory queue, v0.2 does not
recover those events after restart.

## 3. Persistent local SQLite

### 3.1 Purpose and boundary

File-backed SQLite is a supported v0.2 Collector storage mode.

The Repository MUST receive only already-normalized, already-redacted
Canonical values or Canonical event data. It MUST NOT receive raw framework
objects, raw SDK configuration objects, unsanitized input/output values, or
unredacted errors.

The SDK MUST continue to send events through the existing local HTTP
transport. The SDK MUST NOT open, inspect, create, or delete the Collector
database.

The frontend MUST NOT open or inspect the database. It MUST use Query API v1
and v2 only.

### 3.2 Storage modes

The following storage modes are defined:

* `:memory:` is the existing ephemeral mode.
* A filesystem path is the persistent file-backed mode.

The existing programmatic `Repository()` default of `:memory:` MUST remain
valid for v0.1-compatible callers and tests. The new `tracemotive serve`
command uses a persistent default path unless the user explicitly selects
`:memory:`.

An empty path, whitespace-only path, directory path, or path that cannot be
opened MUST fail before the HTTP server starts. The error MUST be safe and
MUST NOT contain captured content or secret values.

### 3.3 Public path configuration

The v0.2 server-facing configuration is:

```text
tracemotive serve [--db PATH] [--port PORT]
```

The environment variable `TRACEMOTIVE_DB` MAY provide the database path when
`--db` is absent.

Resolution order is normative:

1. `--db PATH`, when provided;
2. `TRACEMOTIVE_DB`, when non-empty;
3. the platform default path in §3.4.

The SDK `configure()` API MUST NOT gain a database path parameter. Database
selection belongs to the Collector/backend process, not the SDK/integration
process.

The special value `:memory:` MUST select an in-memory database only when it is
provided explicitly through `--db`, `TRACEMOTIVE_DB`, or the existing
programmatic Repository path.

### 3.4 Safe default path

When no path is explicitly configured, `tracemotive serve` MUST resolve the
following path:

| Platform | Default database path |
|---|---|
| Windows | `%LOCALAPPDATA%\TraceMotive\tracemotive.sqlite3` |
| macOS | `~/Library/Application Support/TraceMotive/tracemotive.sqlite3` |
| Linux and other POSIX | `$XDG_DATA_HOME/tracemotive/tracemotive.sqlite3` when `XDG_DATA_HOME` is set; otherwise `~/.local/share/tracemotive/tracemotive.sqlite3` |

On Windows, if `LOCALAPPDATA` is unavailable, the implementation MUST use the
user profile's local application-data directory obtained from the platform's
standard user path. It MUST NOT fall back to the repository checkout, the
current working directory, or a shared system directory.

On POSIX, the implementation MUST create the parent directory if needed and
MUST request user-only permissions for newly created directories and files.
The exact permission enforcement mechanism is platform-specific, but a newly
created database MUST NOT intentionally be world-readable or group-readable.

The resolved path MAY be printed as a startup fact. The printed path MUST NOT
include trace content, credentials, or database contents.

### 3.5 Database opening and startup order

The persistent server MUST perform startup in this order:

1. Resolve and validate the database path.
2. Open SQLite.
3. Inspect `schema_migrations`.
4. Apply all known forward migrations transactionally.
5. Verify that the database can be queried.
6. Construct the Collector and Query API.
7. Construct the production UI routes.
8. Bind the loopback HTTP server.

If steps 1–5 fail, the HTTP server MUST NOT bind or advertise readiness.

The health endpoint MUST return healthy only after the configured database is
open, migrated, and queryable.

### 3.6 Migration strategy

The existing `schema_migrations` table and forward-only migration policy
remain authoritative.

Each migration MUST:

* have one monotonically increasing integer version;
* run in a transaction where supported by SQLite;
* be recorded only after successful completion;
* leave existing valid trace/span data intact unless a future v0.2
  specification explicitly authorizes a non-destructive transformation.

If the database version is newer than the running binary understands, startup
MUST be refused and the database MUST remain unmodified.

File-backed support alone MUST NOT force a schema migration. The first v0.2
implementation SHOULD reuse the existing v0.1 schema and migration version
unless a separately specified feature requires a new table or index.

Package version `0.2.x`, Canonical schema version `0.1`, and SQLite migration
version MUST remain independently reported and interpreted.

### 3.7 SQLite journal and sidecar handling

The v0.2 public contract does not require WAL mode. An implementation MAY use
SQLite rollback journaling or WAL if it preserves the defined behavior.

Any SQLite sidecar created by the implementation, including but not limited
to `-journal`, `-wal`, or `-shm`, is part of the local persistence boundary
while it exists. Privacy validation MUST inspect the main database and every
sidecar created for the configured database path.

The implementation MUST NOT claim that deleting only the main `.sqlite3`
file is a complete secure erase operation. SQLite sidecar lifecycle is an
operational detail, and local filesystem recovery is outside TraceMotive's
security guarantees.

### 3.8 Restart and durability semantics

After a successful ingest response, the corresponding accepted state MUST be
committed to the configured Repository transaction according to the existing
v0.1 ingest contract.

After a normal Collector shutdown and restart using the same database path:

* persisted Traces MUST remain queryable;
* persisted Spans and separated Span I/O MUST remain queryable;
* event idempotency records MUST remain available;
* migration version MUST remain available;
* Canonical timestamps, numbers, nulls, and CaptureInfo MUST round-trip;
* a retried event with the same event ID and same content MUST retain v0.1
  duplicate semantics.

An abnormal process termination, machine failure, or filesystem failure does
not create a stronger durability guarantee than SQLite commit semantics.

### 3.9 Deletion semantics

The existing `DELETE /api/v1/traces/{trace_id}` contract MUST remain unchanged.

Deletion MUST:

* be transactional;
* remove the Trace;
* remove associated Spans;
* remove associated Span I/O;
* remove associated ingest event records;
* return `204 No Content` for an existing or nonexistent Trace;
* leave no v0.2 tombstone or permanent ingest blocklist.

After deletion, a later valid event MAY recreate the same canonical Trace or
Span state. A delayed SDK event MAY therefore make a deleted Trace reappear.
This is an existing v0.1 behavior and is not changed by persistence.

V0.2 MUST NOT add automatic retention, archival, or whole-database deletion
commands.

### 3.10 Persistent storage privacy contract

The privacy order remains:

```text
framework value
  -> Canonical normalization
  -> redaction/sanitization
  -> size handling
  -> serialized Canonical event
  -> in-memory transport queue
  -> HTTP ingest
  -> Repository transaction
  -> SQLite main database and possible sidecars
```

A Repository regression test MUST prove that an intentionally supplied
recognizable secret is absent from:

* the main SQLite file;
* any `-journal` file created during the write;
* any `-wal` file created during the write;
* any `-shm` file created during the write;
* any other SQLite sidecar identified from the configured database basename.

The test MUST check both while the relevant transaction/journal state exists,
where the test can safely control it, and after Repository close.

TraceMotive MUST NOT claim to provide local database encryption, secure erase,
or detection of every unknown secret. Users remain responsible for deciding
whether captured local content is appropriate for their filesystem.

## 4. `tracemotive serve`

### 4.1 Command contract

The v0.2 command is:

```text
tracemotive serve [--db PATH] [--port PORT]
```

Default port is `8765`.

`PORT` MUST be an integer from `1` through `65535`. If the port cannot be
bound, the command MUST exit non-zero and MUST NOT claim healthy service.

### 4.2 Host contract

The v0.2 command MUST NOT expose a configurable `--host` option. The server
bind address is fixed to the IPv4 loopback literal `127.0.0.1`.

This restriction is intentional: a host option adds no required local-user
capability and creates an avoidable remote-exposure contract.

The command MUST reject an invocation containing `--host`, including values
that appear loopback-like. Existing direct Uvicorn development commands and
the v0.1 Collector binding contract remain separate compatibility paths.

The v0.2 server MUST NOT bind to or document:

* `0.0.0.0`;
* `::`;
* a LAN or public IP address;
* a hostname resolved through DNS;
* any remote hostname;
* an HTTP or HTTPS endpoint supplied by a user.

The SDK transport endpoint remains governed by the v0.1 loopback HTTP
validation rules.

### 4.3 Application routes

The production server MUST expose:

* the existing `POST /api/v1/ingest` route;
* every existing v0.1 `/api/v1` Query API route;
* the v0.2 comparison routes in `/api/v2`;
* `GET /` for the packaged frontend entry point;
* packaged static asset routes below the frontend asset namespace.

API routes MUST be registered before the catch-all frontend route.

The frontend MUST issue relative `/api/...` requests in production. A
production build MUST NOT hard-code a development port or remote Collector
URL.

The server MUST NOT expose arbitrary filesystem paths or directory listings.

### 4.4 Static asset serving

The production UI MUST be served from package-owned static assets installed
inside the TraceMotive wheel.

The server MUST serve:

* an immutable packaged `index.html` at `/`;
* only packaged CSS, JavaScript, media, and asset files;
* no source TypeScript files;
* no `node_modules` contents;
* no source maps unless they are explicitly included by the release policy.

The UI MUST use hash routing or an equivalent packaged-route strategy that
does not require the server to expose arbitrary paths. A request for an
unknown non-API path MUST return the packaged frontend entry point only when
it is a valid frontend route; it MUST NOT return a filesystem file selected
by user input.

### 4.5 Shutdown behavior

`tracemotive serve` owns the Repository it creates.

On normal shutdown, including Ctrl-C and the supported process termination
path, it MUST:

1. stop accepting new HTTP requests;
2. allow the active request to finish within the server shutdown budget;
3. close the Collector Repository;
4. close any SQLite connection owned by the command;
5. exit without leaving a TraceMotive worker thread running.

Shutdown MUST be bounded and MUST NOT wait indefinitely. A forced process
termination does not guarantee delivery of SDK transport events or completion
of a database transaction.

The command MUST NOT create a persistent SDK spool during shutdown.

### 4.6 Server failure isolation

A server startup failure is a command failure and MUST be reported by a
non-zero process exit. It MUST NOT be converted into a falsely healthy server.

Once an Agent process is running, Collector or transport failures continue to
obey the v0.1 rule that tracing failure MUST NOT fail Agent execution.

Error output MUST be generic and safe. It MUST NOT include captured content,
raw request bodies, authorization values, or stack traces in HTTP responses.

## 5. Frontend build and release contract

### 5.1 Responsibility split

Node.js and npm are development/release-build dependencies only.

Normal TraceMotive users installing a released wheel MUST NOT need Node.js,
npm, Vite, or the frontend source tree.

The existing frontend development workflow MAY continue to use Vite and a
loopback development proxy.

### 5.2 Reproducible build pipeline

The production asset pipeline is normative:

```text
clean checkout
  -> npm ci in frontend/
  -> deterministic production build
  -> copy/build assets into package-data directory
  -> build sdist and wheel
  -> fresh isolated wheel install
  -> run tracemotive serve without Node/npm
```

The release process MUST use `npm ci`, not an unconstrained `npm install`, so
`frontend/package-lock.json` is authoritative for resolved frontend
dependencies.

The production build MUST:

* use the committed frontend source and lockfile;
* use production mode;
* use a fixed supported Node.js toolchain in CI/release validation;
* avoid timestamps, random IDs, local absolute paths, development URLs, and
  machine-specific values in generated application assets;
* produce the same application asset bytes for the same source, lockfile,
  Node/npm toolchain, and build inputs.

The generated production assets MUST be copied into a package-data directory
under the `tracemotive` package before wheel construction. The wheel MUST
contain the frontend entry point and all referenced hashed assets.

The wheel MUST NOT contain `frontend/node_modules`, the frontend test suite,
or an unbuilt development-only frontend in place of production assets.

### 5.3 Fresh-install gate

This is a release-readiness gate owned by V02-90. It is not required in full
on every Normal CI run, although Normal CI MUST retain a representative
package smoke.

The release gate MUST:

1. build an actual sdist and wheel;
2. inspect the actual wheel contents;
3. create a fresh isolated environment outside the repository checkout;
4. install the wheel with the server capability;
5. ensure the test process does not import source-tree TraceMotive modules;
6. ensure Node.js/npm are not required by the installed server;
7. launch `tracemotive serve` against a temporary file-backed database;
8. poll `GET /api/v1/health` until ready;
9. fetch `/` and at least one packaged asset;
10. ingest and query a deterministic trace through the same origin;
11. terminate the server with bounded waits;
12. restart it using the same database and verify persistence.

The gate MUST fail if the wheel lacks package assets, if the server imports
the repository checkout, or if frontend startup requires a separate Node/npm
process.

### 5.4 Frontend safety

The production UI MUST preserve the v0.1 safety rules:

* captured content is rendered as inert text/data;
* no `dangerouslySetInnerHTML` or equivalent execution path is introduced;
* API error bodies are not rendered verbatim;
* API requests are same-origin in production;
* exact integer and decimal values remain lossless at the wire boundary;
* `0` remains distinct from `null`.

## 6. Trace comparison

### 6.1 Purpose and non-purpose

Trace comparison describes observed differences between two persisted
Canonical Traces.

It MUST NOT claim:

* root cause;
* causal proof;
* failure responsibility;
* semantic correctness of either Agent result;
* that one model, tool, or Span caused another difference;
* that any displayed ordering is causal ordering;
* first observed difference or first divergence;
* causal ranking or a root cause candidate.

Comparison is read-only. It MUST NOT modify Traces, Spans, ingest history,
CaptureInfo, or database migration state.

### 6.2 Endpoint

The v0.2 comparison endpoint is:

```text
GET /api/v2/compare/{left_trace_id}/{right_trace_id}
```

`left_trace_id` is the baseline/display-left Trace. `right_trace_id` is the
candidate/display-right Trace. The endpoint MUST NOT call either side
"correct", "expected", or "causal".

The endpoint MUST:

* validate both Canonical Trace IDs;
* reject equal IDs with `400 Bad Request`;
* return `404 Not Found` if either Trace is absent;
* return `413 Payload Too Large` if the configured comparison limits are
  exceeded;
* return a generic `500` response for an internal failure;
* never expose raw exception text or database paths.

Every comparison error response MUST have this exact JSON shape:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "invalid request"
  }
}
```

The status-to-code mapping is fixed:

| HTTP status | `error.code` | `error.message` |
|---|---|---|
| 400 | `invalid_request` | `invalid request` |
| 404 | `not_found` | `not found` |
| 413 | `comparison_too_large` | `comparison too large` |
| 500 | `internal_error` | `internal error` |

The error message MUST be the exact lowercase ASCII value shown above. The
response MUST NOT include a Trace ID, database path, exception class, stack
trace, or request-body value beyond what is already present in the URL.

The endpoint MUST read both Traces and their Spans within one consistent
Repository read snapshot. A concurrent delete after the read snapshot MAY
complete independently, but it MUST NOT produce a mixed left/right response.

### 6.3 Comparison limits

The initial implementation MUST enforce:

* at most 10,000 persisted Spans per input Trace;
* at most 4,096 emitted difference records;
* at most 4 MiB serialized comparison response body.

When a limit is exceeded, the endpoint MUST return `413` and MUST NOT return
a partial comparison response. The error body MUST use a safe generic code
and message.

### 6.4 Response shape

A successful response MUST have this top-level shape:

```json
{
  "comparison_version": "0.2",
  "left_trace": {},
  "right_trace": {},
  "summary": {},
  "spans": [],
  "ambiguous_groups": [],
  "unavailable_spans": []
}
```

The response MUST contain no framework object, ingest event, SQLite row, raw
exception, or unsanitized value.

`left_trace` and `right_trace` MUST contain the existing Query API Trace
header plus its existing derived summary statistics. They MUST preserve exact
Canonical timestamp and numeric wire representations.

`summary.trace_fields` MUST contain field results for:

* `status`;
* `ended_at`;
* `latency_ms`;
* `span_count`;
* `error_count`;
* `llm_call_count`;
* `input_tokens`;
* `output_tokens`.

Summary results MUST be emitted in exactly the order listed above.

`summary.alignment` MUST have this exact shape:

```json
{
  "matched_spans": 14,
  "left_only_spans": 2,
  "right_only_spans": 3,
  "ambiguous_groups": 1,
  "unavailable_spans": 0
}
```

The alignment counts MUST be integers greater than or equal to zero.
`matched_spans` counts `exact_match` Span results. `left_only_spans` and
`right_only_spans` count structurally usable Spans that have no counterpart.
`ambiguous_groups` counts group records in `ambiguous_groups`, and
`unavailable_spans` counts records in `unavailable_spans`. An ambiguous or
unavailable local result MUST NOT make the entire comparison fail or become
inconclusive.

`summary.difference_count` MUST equal the number of records in all
`spans[*].differences`. `summary.uncertainty_count` MUST equal the number of
records in all `spans[*].uncertainties` plus the number of
`unavailable_spans` records plus the number of `ambiguous_groups` records.
These counts are reporting fields only; they do not provide causal ranking.

Each summary result MUST use this shape:

```json
{
  "path": "status",
  "state": "same",
  "left": "ok",
  "right": "ok",
  "reason": null
}
```

Allowed `state` values are:

* `same` — both values are present and exactly equal under Canonical JSON
  comparison;
* `different` — both values are present and not equal;
* `unknown` — the comparison cannot establish equality or difference;
* `left_only` — only the left value exists;
* `right_only` — only the right value exists.

`left` and `right` MUST be present as JSON fields. A JSON `null` value is a
real observed value when `state` is `same` or `different`; it MUST NOT be
used to mean that a side is absent. Absence is represented by the state.

Allowed field-result `reason` values are `null`, `capture_unavailable`,
`redacted_observation`, `missing_side`, `unsupported_observation`, and
`comparison_limit`.

`status`, `ended_at`, `span_count`, `error_count`, and `llm_call_count` are
directly observed or deterministically derived values. Their JSON `null`
values, when permitted by the v0.1 Query API, are compared as observed
values. `latency_ms`, `input_tokens`, and `output_tokens` are known only when
their v0.1 derivation has a known result on that side. If either side's value
is unknown, the result MUST be `unknown` even when both serialized values are
`null`; it MUST use the applicable reason rather than claiming equality.

### 6.5 Span alignment inputs

Canonical `trace_id` and `span_id` MUST NOT be used as cross-run alignment
identity. Canonical IDs are execution-local identifiers.

`source.native_trace_id`, `source.native_span_id`, and
`source.native_parent_span_id` MUST NOT participate in v0.2 P0 alignment.
Their presence in stored Canonical data is display-only for this feature.

Alignment MUST use only data available through the Query API/Repository
boundary. Framework objects and framework-private metadata MUST NOT be loaded
to improve alignment.

The P0 alignment algorithm is Simple Structural Alignment v1. A future
extension MAY use a verified framework-native identity as an additional
signal only after a separate specification and compatibility evidence prove
run-to-run stability. That future signal MUST NOT change the v0.2 P0 result
for the same Canonical input.

### 6.6 Simple Structural Alignment v1

Simple Structural Alignment v1 is the only alignment algorithm in the v0.2
P0 contract. It is deliberately structural and MUST NOT claim that two
`exact_match` Spans are the same real-world operation.

For each Span whose observed parent chain is complete and acyclic, define:

```text
segment = (type, operation, name, ordinal)
parent_path = ordered ancestor segments, excluding the Span itself
alignment_key = (parent_path, type, operation, name, ordinal)
```

For a root Span, `parent_path` is the empty sequence. `ordinal` is a
zero-based structural ordinal among same-parent siblings with the same
`(type, operation, name)` signature. Ordinals MUST be calculated separately
for each compared Trace using this exact order:

1. `started_at` ascending by exact Canonical timestamp value;
2. `span_id` ascending as the deterministic tie-breaker.

The key MUST contain no Canonical parent ID and no framework-native ID.
Ordinal is a deterministic structural convention, not proof of semantic
identity. In particular, ordinal position alone MUST NOT establish an
individual exact pair when either side has multiple same-signature siblings
under the same aligned parent.

The alignment operation MUST be hierarchical and MUST be local to the
affected sibling group:

1. Build the Span forest separately for the left and right Trace. A synthetic
   root is the aligned parent for root Spans.
2. Begin with structurally usable root groups and then process children only
   under an aligned parent. A non-root parent is aligned only when it has an
   `exact_match` result or when a future specification-approved deterministic
   signal uniquely resolves that parent.
3. Under each aligned parent, group immediate children on each side by the
   signature `(type, operation, name)`. The group identity MUST NOT include
   ordinal.
4. When a signature group contains exactly one Span on each side, the normal
   exact structural key MAY establish one `exact_match` result. The result's
   complete semantic path still contains the deterministic ordinal.
5. When either side contains more than one Span in the same signature group,
   ordinal MUST NOT establish an individual pair. The implementation MUST
   emit one localized `ambiguous_group` record for the group. V02-20 has no
   additional member-resolving signal, so `resolved_members` MUST be empty
   for such a group.
6. A signature group containing exactly one Span on only one side MAY emit an
   individual `left_only` or `right_only` result. A member of a repeated
   group MUST NOT be converted to `left_only` or `right_only` merely because
   the two group counts differ; those counts are populated only when the
   side-only membership is independently deterministic.
7. A Span whose key cannot be computed because of a missing parent, a cycle,
   or invalid structural data MUST emit an `unavailable` record.
8. Children of an ambiguous parent MAY emit `unavailable` records with reason
   `ambiguous_parent` when their parent identity cannot be resolved. Such
   unavailability MUST be limited to the affected ambiguous subtree.

An individually resolved member in a repeated group is permitted only when
another deterministic signal is explicitly approved by a later v0.2
specification and uniquely identifies that member without guessing. Native
IDs, timestamp-nearest matching, input/output similarity, name similarity,
and heuristic or confidence signals are not such signals in V02-20.

No alignment guess, nearest-neighbor match, timestamp tolerance, name
similarity, native-ID fallback, or cross-branch inference is permitted.

If a future specification introduces heuristic suggestions, exact structural
results and suggested/heuristic results MUST be separate result layers. A
heuristic suggestion MUST NOT be serialized or displayed as a confirmed
`exact_match` result.

An ambiguous group or unavailable Span is a local result. It MUST NOT prevent
matching or field comparison for a different branch whose keys are usable.
No whole-comparison `inconclusive` state is defined for v0.2 P0.

### 6.7 Alignment result records

`spans` contains one item for every exact, left-only, or right-only Span
result. Each item MUST have this shape:

```json
{
  "alignment": "exact_match",
  "semantic_path": [],
  "left": {"trace_id": "...", "span_id": "..."},
  "right": {"trace_id": "...", "span_id": "..."},
  "differences": [],
  "uncertainties": []
}
```

Allowed `alignment` values are `exact_match`, `left_only`, and `right_only`.
`summary.alignment.matched_spans` counts only `exact_match` records. For
`left_only` and `right_only`, the absent side MUST be JSON `null`. No
synthetic Span may be created. A Span belonging to an unresolved repeated
sibling group MUST NOT appear as an `exact_match` record.

`semantic_path` in a Span result MUST be the complete path: its
`parent_path` followed by the Span's own `(type, operation, name, ordinal)`
segment. A root therefore has one segment in `semantic_path`, even though its
alignment key has an empty `parent_path`.

`ambiguous_groups` MUST be an array of records with this shape:

```json
{
  "alignment": "ambiguous_group",
  "parent_path": [],
  "group_signature": {
    "type": "tool",
    "operation": "tool.call",
    "name": "search"
  },
  "left_count": 2,
  "right_count": 3,
  "resolved_members": [],
  "ambiguous_members": {
    "left": [{"trace_id": "...", "span_id": "..."}],
    "right": [{"trace_id": "...", "span_id": "..."}]
  },
  "left_only_count": null,
  "right_only_count": null,
  "reason": "repeated_sibling_ambiguity"
}
```

`parent_path` MUST identify the complete aligned parent path and MUST exclude
the grouped members. `group_signature` MUST contain exactly `type`,
`operation`, and `name`; it MUST NOT contain ordinal or a native identity.
`left_count` and `right_count` MUST equal the total number of group members
on their respective sides. `resolved_members` MUST contain only individually
resolved exact pairs approved by the active specification. Each resolved
member MUST include `left`, `right`, and its complete `semantic_path`.
`ambiguous_members.left` and `ambiguous_members.right` MUST contain every
group member that was not individually resolved. In V02-20 P0, all members of
a repeated group MUST remain in these arrays.

`left_only_count` and `right_only_count` MUST be non-negative integers only
when the corresponding side-only membership is independently deterministic;
otherwise they MUST be JSON `null`. A difference in group cardinality alone
does not establish which logical member is side-only. The only P0 reasons are
`repeated_sibling_ambiguity` and `structural_key_collision`.

`unavailable_spans` MUST be an array of records with this shape:

```json
{
  "alignment": "unavailable",
  "side": "left",
  "span": {"trace_id": "...", "span_id": "..."},
  "reason": "missing_parent"
}
```

Allowed unavailable reasons are `missing_parent`, `cycle`,
`invalid_structure`, and `ambiguous_parent`. Descendants whose own key cannot
be computed MUST be listed separately. An unavailable Span MUST NOT be
silently treated as left-only or right-only. `ambiguous_parent` MUST be used
only for descendants of an unresolved ambiguous group; it MUST NOT mark an
unrelated branch or ancestor unavailable.

### 6.8 Span field comparison

For `exact_match` Spans, differences MUST be evaluated in this fixed field
order:

1. `source.framework`;
2. `source.framework_version`;
3. `source.integration`;
4. `source.integration_version`;
5. `parent_path`;
6. `type`;
7. `operation`;
8. `name`;
9. `status`;
10. `error.type`;
11. `error.message`;
12. `details.kind`;
13. `details.agent_name`;
14. `details.agent_version`;
15. `details.provider`;
16. `details.request_model`;
17. `details.response_model`;
18. `details.response_id`;
19. `details.request_parameters`;
20. `details.usage`;
21. `details.finish_reasons`;
22. `details.estimated_cost`;
23. `details.tool_name`;
24. `details.tool_call_id`;
25. `details.from_agent`;
26. `details.to_agent`;
27. `details.source_type`;
28. `input`;
29. `output`;
30. `capture.input`;
31. `capture.output`;
32. `started_at`;
33. `ended_at`;
34. derived `latency_ms`;
35. `metadata`;
36. `attributes`.

The comparison projection MUST exclude `trace_id`, `span_id`,
`parent_span_id`, `source.native_trace_id`, `source.native_span_id`, and
`source.native_parent_span_id`. Those identifiers are execution-local or
alignment inputs and MUST NOT make an otherwise exact-match observation
differ.
The projection MUST include the specialized Canonical details fields listed
above when the field exists for the Span's details variant. A missing optional
field and an explicit JSON `null` remain distinct according to the existing
Canonical representation.

For an `exact_match` Span, `differences` MUST contain only field results whose
state is `different`, `left_only`, or `right_only`. `uncertainties` MUST
contain field results whose state is `unknown`. A `same` field MUST NOT be
emitted. A field absent on both sides is `same`; a field absent on one side
and present on the other uses `left_only` or `right_only`. Each field result
in either array MUST use the shape shown below, and the arrays MUST follow
the fixed field order above:

```json
{
  "path": "/input",
  "state": "unknown",
  "left": null,
  "right": null,
  "reason": "capture_unavailable"
}
```

For a `left_only` or `right_only` Span, `differences` MUST contain one
record with the empty JSON Pointer path (`""`) and the corresponding
`left_only` or `right_only` state.

Each difference MUST use:

```json
{
  "path": "/details/request_parameters/temperature",
  "state": "different",
  "left": 0,
  "right": 0.7,
  "reason": null
}
```

The JSON Pointer path MUST use RFC 6901 escaping. Object keys MUST be
processed in Canonical lexicographic order. Arrays MUST be compared by exact
index and length; arrays MUST NOT be treated as unordered sets.

`left` and `right` values MUST be redacted Canonical JSON values. Exact
numbers MUST be serialized without lossy conversion.

### 6.9 Content and redaction comparison

Input and output comparison MUST use CaptureInfo before comparing values.

The rules are:

* `captured` on both sides and equal values: `same`;
* `captured` on both sides and unequal values: `different`;
* either side `not_captured`: `unknown` with `capture_unavailable`;
* either side `redacted = true`: comparison MAY report a difference between
  sanitized observations, but MUST include `redacted_observation` and MUST
  NOT claim equality or inequality of the original unredacted values;
* captured JSON `null` is comparable as a known value;
* not-captured `null` is not a comparable value;
* content above the v0.1 size limit remains unknown rather than truncated or
  reconstructed.

The comparison layer MUST NOT re-read raw source content or attempt a second
secret-detection pass over absent values.

### 6.10 Numeric and status comparison

The comparison layer MUST preserve the v0.1 exact-number rules.

In particular:

* token `0` is known zero;
* token `null` is unknown;
* latency is derived from exact timestamps;
* a missing end timestamp produces unknown latency;
* status values are compared as observed status values;
* a child Span error MUST NOT be promoted to a Trace failure by comparison;
* comparison MUST NOT infer successful semantic output from `status = ok`.

### 6.11 Deterministic result ordering

Comparison ordering is a presentation and reproducibility rule. It is not a
causal, wall-clock, or first-divergence rule.

The `spans` array MUST be ordered by the structural forest traversal:

1. roots before descendants;
2. roots and same-parent children by `(type, operation, name, ordinal)` using
   Unicode code-point lexicographic order for strings;
3. parent before child;
4. left-only and right-only results at the key's structural position;
5. field results within each Span by the fixed §6.8 field order;
6. object members by Canonical lexicographic key order and arrays by ascending
   index.

`ambiguous_groups` MUST be ordered by
`(parent_path, type, operation, name)`. Within each group, member references
MUST be ordered by `(started_at, span_id)` separately on each side, and
`resolved_members` MUST use that same structural order. `unavailable_spans`
MUST be ordered by `(side, started_at, span_id)`, with `left` before `right`.

Parallel spans, fan-out, and fan-in do not change these rules. The ordering
only makes the returned evidence reproducible. No response or UI MAY call
this order first, earlier, preceding, or otherwise causal.

### 6.12 Deferred causal and first-difference research

The following are not part of the v0.2 P0 response or UI:

* first observed difference;
* first divergence;
* causal ranking;
* root cause candidate;
* causal proof;
* automatic RCA.

The v0.2 P0 response MUST NOT include a `first_observed_difference` field or
an equivalent field under another name. Existing Issue #1
first-divergence exploration MAY later define a separate additive contract.
That work is not a dependency of V02-20, V02-21, or V02-22.

### 6.13 No causal claims

No comparison response, UI label, log message, or documentation MAY state or
imply that:

* the first candidate caused a later failure;
* a left/right difference is responsible for the outcome;
* an `exact_match` Span is the same real-world operation across runs;
* a missing or redacted value was equal to any other value;
* a different model or parameter would have produced a particular outcome;
* a structural response ordering identifies a causal origin.

Any future causal feature requires a separate specification revision.

## 12. Explicitly unresolved or intentionally implementation-defined items

The following are intentionally not public behavior choices for v0.2:

* SQLite rollback journal versus WAL mode;
* internal module and class names;
* exact FastAPI/Starlette static-serving implementation;

These choices MUST NOT change any normative behavior in this document or the
Frozen v0.1 contract.

The following are not unresolved implementation details; they are explicit
v0.2 decisions:

* `tracemotive serve` has no `--host` option and binds only to `127.0.0.1`;
* `Repository()` remains memory-default for v0.1-compatible programmatic use;
* `tracemotive serve` defaults to file-backed storage;
* `/api/v1` remains unchanged;
* comparison uses `/api/v2`;
* P0 alignment uses only Simple Structural Alignment v1;
* native identity is excluded from P0 alignment;
* ordinal alone never establishes an individual exact pair in a repeated
  same-signature sibling group;
* repeated sibling groups are reported with localized ambiguity and member
  counts before any field diff is shown;
* the production result categories are `exact_match`, `left_only`,
  `right_only`, `ambiguous_group`, and `unavailable`;
* ambiguous groups and unavailable Spans are localized;
* local uncertainty does not make the whole comparison inconclusive;
* first-difference and causal-research output is deferred;
* SQLite encryption is not provided or claimed;
* persistent SDK spool is not provided.

## 13. Final v0.2 design rule

TraceMotive v0.2 MUST make observed local evidence more durable and more
useful without turning derived comparison into a causal claim.

The stable boundary remains:

```text
Framework adapter -> Canonical observation -> local transport -> Collector
-> SQLite -> Query API -> inert UI
```

Persistent storage preserves sanitized observation. Comparison describes
observable differences and uncertainty. Neither changes the meaning of the
existing Canonical Trace, Span, privacy, transport, or v0.1 Query API
contracts.

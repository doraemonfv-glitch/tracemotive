# TraceMotive v0.3 Proposed Specification

Status: Proposed
Specification version: `0.3-proposed`
Deliverable: `V03-00`
Target package version: `0.3.x`
Canonical schema version: `"0.1"`
Ingest protocol version: `1`
Existing Query API: `/api/v1`
Existing comparison API: `/api/v2`, comparison version `0.2`
Proposed comparison API: `/api/v3`, comparison version `0.3`

This document is a release-design contract, not an implementation. Creating
this document MUST NOT change production code, package metadata, the Frozen
v0.1 specification, the v0.2 comparison behavior, or the repository database
schema.

---

## 1. Status and authority

This document proposes the TraceMotive v0.3 contract. It is not frozen.

The authority order for later v0.3 implementation work is:

1. `spec/v0.1-frozen-spec.md` for all existing v0.1 behavior;
2. `AGENTS.md` for repository rules and security boundaries;
3. this document for additive v0.3 behavior;
4. the existing v0.2 implementation and `spec/v0.2-proposed-spec.md` as the
   compatibility baseline;
5. `docs/long-term-vision.md` and advisory reviews only as non-normative
   context.

If this document conflicts with the Frozen v0.1 specification, the v0.1
specification wins. If a proposed v0.3 feature cannot be implemented from
the Canonical observations and public framework APIs available at the stated
boundary, the feature MUST be narrowed or deferred rather than inferred.

The terms MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative.

The v0.3 proposal is intentionally additive:

* v0.1 Canonical objects, privacy rules, transport, ingest protocol, SQLite
  persistence, and `/api/v1` remain the compatibility foundation;
* v0.2 persistence, packaged UI, `/api/v2` comparison, and localized
  ambiguity remain available;
* v0.3 adds an insight read model and one additional adapter only after the
  relevant validation gates pass.

## 2. Product thesis

TraceMotive v0.3 should answer one narrow question exceptionally well:

> A working agent run and a failing agent run differ. Where did the observed
> executions first meaningfully diverge, what changed around that point, and
> what should I inspect first?

The product promise is an investigation starting point, not a causal verdict.
In this document, the product-facing phrase “first meaningful divergence” is
shorthand for an evidence-supported behavioral divergence selected by the
rules in §§7.4 and 10. It does not mean that TraceMotive knows the difference
was important to the user's task.

The v0.3 result MUST be phrased as observed evidence. It MUST never sound more
certain than the underlying alignment, capture, and lifecycle evidence allows.

The product remains:

* local-first;
* privacy-first;
* deterministic wherever the Canonical evidence permits;
* uncertainty-aware;
* framework-independent after the adapter boundary;
* non-fatal to the instrumented Agent;
* conservative about causal language.

The strategic focus is:

```text
good run + bad run
        -> first safe investigation starting point
        -> observed evidence around that point
        -> detailed comparison when needed
```

v0.3 is not an attempt to become a general observability platform.

## 3. User problem

The v0.2 product can show structural observed differences between two traces.
It deliberately does not identify a first divergence. A user must currently
scan the comparison, interpret alignment limitations, and decide which
difference deserves attention.

The v0.3 user needs a short path from selection to investigation:

1. select a working or baseline run and a failing or candidate run;
2. see whether a reliable first meaningful divergence exists;
3. see the exact observed field, group, or status evidence supporting it;
4. see later observations in the same structural region without being told
   that they were caused by the first finding;
5. jump to the existing detailed span and field comparison;
6. understand what is ambiguous, unavailable, redacted, or incomplete.

The product MUST support runs where:

* both runs succeed;
* one run fails;
* both runs fail for different reasons;
* both runs fail in the same observed way;
* one run is incomplete;
* content is disabled or unavailable on either side;
* repeated structurally identical siblings cannot be safely paired;
* framework metadata differs without behavioral evidence changing.

## 4. v0.2 baseline

### 4.1 Current supported product

The current repository describes TraceMotive v0.2 as a local-first tracing and
debugging tool with:

* sanitized Canonical traces and spans;
* persistent local SQLite storage through the Collector;
* `tracemotive serve` with packaged UI assets;
* no Node.js/npm requirement for installed-wheel runtime use;
* OpenAI Agents SDK integration in the declared `>=0.17,<0.18` range;
* read-only `/api/v1` trace queries;
* read-only `/api/v2/compare/{left_trace_id}/{right_trace_id}`;
* Simple Structural Alignment v1;
* field-level observed differences;
* localized `ambiguous_group` and `unavailable` records.

### 4.2 Canonical evidence available today

The v0.1 Canonical model exposes enough evidence for a narrow v0.3 P0:

* Trace status, timestamps, source, and deterministic derived statistics;
* Span type, operation, name, status, error, timestamps, parent relationship,
  source, metadata, and attributes;
* LLM provider/model/request-parameter/usage observations when an adapter has
  them;
* Tool name and tool input/output observations when an adapter has them;
* CaptureInfo for input and output, including captured JSON `null`, disabled,
  source unavailable, not-yet-available, serialization failure, size limit,
  and redaction provenance;
* deterministic structural parent paths when the persisted span forest is
  complete and acyclic.

### 4.3 v0.2 limitations that v0.3 MUST preserve

The v0.2 aligner intentionally does not treat Canonical IDs or framework IDs
as cross-run identity. It does not use timestamp-nearest matching, similarity,
or heuristic pairing. A repeated same-signature sibling group is ambiguous
when ordinal position cannot establish individual identity. Descendants of an
ambiguous or structurally unavailable parent remain locally unavailable.

The v0.2 comparison is observed structural evidence. It does not claim:

* first observed difference;
* first meaningful divergence;
* causal order;
* responsibility;
* root cause;
* causal proof;
* semantic correctness of either result.

v0.3 MAY add a finding at a repeated group coordinate when the group-level
observation itself is deterministic, such as a changed member count. It MUST
NOT turn that group-level finding into an exact member pairing.

### 4.4 Existing test and release baseline

The v0.3 implementation plan MUST retain and extend, rather than weaken, the
current coverage for:

* alignment evaluation and repeated-sibling ambiguity;
* comparison API determinism and read-only behavior;
* persistent SQLite restart, migration, deletion, and sidecar privacy;
* exact numbers, `null` versus zero, and CaptureInfo round trips;
* packaged-wheel runtime without Node.js/npm;
* loopback-only serving;
* full-stack public SDK -> Collector -> SQLite -> Query API -> UI behavior;
* redaction provenance and non-fatal tracing failures.

## 5. v0.3 goals

### 5.1 CORE P0 goals

The Core v0.3 release MUST deliver:

1. a deterministic, evidence-supported behavioral divergence result;
2. deterministic diagnostic findings with structured evidence;
3. an evidence and investigation summary that recommends where to inspect;
4. an insight-first comparison API while preserving v0.2 detail;
5. an insight-first comparison UI that makes uncertainty prominent;
6. a no-key, no-model, no-Node demo path;
7. adversarial false-confidence evaluation;
8. documentation and release gates that preserve all v0.1/v0.2 invariants.

### 5.2 CORE P0 success condition

On a clean local installation, a user should be able to reach a useful Core
deterministic comparison result in under two minutes without an API key,
external model request, repository clone, or Node.js/npm runtime dependency.

This is a release-gate target measured by the demo harness. It is not a claim
that every machine or installation will meet the same wall-clock time.

### 5.3 CONDITIONAL P1 goals

The following work is valuable but MUST NOT delay the Core good-run-vs-bad-run
debugging workflow:

* V03-40/V03-41 LangGraph adapter and real-run validation;
* V03-60 broader scale and workload characterization;
* V03-70 additional product/documentation polish not required by the Core
  release gate.

LangGraph is valuable evidence of framework independence, but it is
conditional P1 work. If its validation becomes technically risky or
destabilizing, it MAY move to v0.3.1 without blocking the Core v0.3 release.

Basic performance regression validation remains required for Core v0.3. The
broader V03-60 workload matrix MAY move to v0.3.1 if it delays the Core
debugging workflow.

v0.3 does not define threshold query parameters or thresholded latency/token
finding types. The existing v0.2 metrics remain available as exact observed
detail, but threshold policy is deferred to a later specification.

## 6. Non-goals

v0.3 MUST NOT add:

* cloud hosting or hosted storage;
* organizations, teams, accounts, billing, or authentication;
* remote Collector support;
* unrestricted or configurable remote binding;
* distributed tracing, span links, or OTLP/OpenTelemetry export;
* replay, execution forking, or intervention experiments;
* automatic LLM-generated RCA;
* causal proof, root-cause claims, or failure responsibility attribution;
* a causal evidence graph or causal edge API;
* a general evaluation, benchmark, dataset, or prompt-management platform;
* generic monitoring dashboards or alerting;
* broad framework expansion;
* automatic retention, archival, or deletion tombstones;
* persistent SDK offline spooling;
* streaming token/chunk persistence;
* a new framework-specific Canonical schema;
* native framework IDs as unconditional cross-run identity;
* an ordinal-only exact pairing inside repeated sibling groups;
* automatic retry claims when the Canonical model does not expose retry
  semantics.

The words `cause`, `caused`, `root cause`, `proven`, `definitive`, and `blame`
MUST NOT be used for v0.3 findings, UI labels, API fields, logs, or user
documentation when they describe a comparison result.

## 7. Terminology

### 7.1 Run and sides

* **Trace** means one persisted Canonical execution observation.
* **Left** means the first trace in the comparison. It is a display/reference
  side, not automatically correct or expected.
* **Right** means the second trace. It is a display/reference side, not
  automatically failing or responsible.
* **Baseline** and **candidate** MAY be used in the UI only when the user has
  explicitly chosen those labels. The API MUST continue to expose left/right
  identity.

### 7.2 Alignment

* **Structurally resolved span** means a span whose parent chain is complete,
  acyclic, and uniquely aligned under the active v0.2 structural rules.
* **Repeated sibling group** means immediate children under one aligned parent
  with the same `(type, operation, name)` signature where either side has more
  than one member.
* **Ambiguous group** means a repeated sibling group for which individual
  members cannot be safely paired.
* **Structural coordinate** means the deterministic tree position used to
  order a finding. It is a presentation/alignment coordinate, never causal
  time and never proof of real-world identity.
* **Group coordinate** means a parent path plus a repeated signature and does
  not contain a member ordinal.

### 7.3 Evidence and certainty

* **Observed evidence** means a value or structural fact represented by the
  sanitized Canonical data or a deterministic derivation explicitly allowed
  by this specification.
* **Confirmed observation** means both the relevant observation and the
  comparison needed for the finding are available without an ambiguity,
  capture, redaction, or incomplete-trace limitation.
* **Observation-limited** means a sanitized difference or group fact is
  visible, but the original value or individual identity is not fully known.
* **Unknown** means the available data cannot establish equality or
  inequality.
* **Unavailable** means the required structural or lifecycle observation is
  not available.
* **Investigation starting point** means a recommended place to inspect first;
  it is not a causal origin.

### 7.4 First meaningful divergence

The relevant normative concept is an **evidence-supported behavioral
divergence**: a difference or safely one-sided observation from the behavioral
signals admitted in §10.2, supported by available Canonical evidence and not
blocked by an applicable uncertainty barrier.

The product-facing phrase **first meaningful divergence** MAY remain, but it
means only:

> the first behavioral divergence, according to deterministic structural
> triage order, that TraceMotive can support from available observations.

It MUST NOT mean semantically important, task-relevant, causal, the failure
origin, or root cause. It is not the first timestamp difference, first field
difference, first JSON inequality, or first ordinal mismatch. The current
Canonical model cannot determine whether a changed tool value mattered to the
user's task or caused a later failure. The API and UI MUST call it an observed
difference selected as a supported place to investigate.

### 7.5 Relationship language

`observed_after`, `same_structural_region`, `descendant_evidence`, and
`terminal_summary` describe deterministic evidence relationships only. They
MUST NOT be rendered or interpreted as `caused_by`.

## 8. Compatibility contract

### 8.1 Version identities

| Boundary | v0.3 contract |
|---|---|
| Package version | `0.3.x` when a later release is actually implemented |
| Canonical schema | remains `"0.1"` |
| Ingest protocol | remains `1` |
| Existing query routes | `/api/v1`, unchanged |
| Existing comparison route | `/api/v2`, unchanged and supported |
| New comparison route | `/api/v3`, comparison version `"0.3"` |
| Python SDK core surface | existing `configure`, `trace`, `span`, `flush` semantics remain |
| Existing OpenAI range | remains `openai-agents>=0.17,<0.18` unless separately specified |
| LangGraph admission | no public range until V03-41; the initial validation candidate is `langgraph==1.2.9` |

The package version MUST NOT be mechanically substituted for the Canonical,
ingest, or comparison version. A v0.3 package MAY continue to persist
Canonical schema `0.1` events and send ingest protocol `1` envelopes.

### 8.2 Existing routes

`/api/v1` MUST remain compatible with the Frozen v0.1 Query API. Existing
`/api/v2/compare/{left_trace_id}/{right_trace_id}` MUST remain available with
its v0.2 response and error semantics. `/api/v2` MUST NOT gain v0.3 fields,
new finding meanings, or altered ambiguity behavior.

The frontend MAY add a v0.3 page or switch its comparison page to `/api/v3`,
but the existing detailed v0.2 comparison data MUST remain reachable from the
v0.3 experience.

### 8.3 Canonical and ingest compatibility

The v0.3 P0 comparison engine MUST consume persisted Canonical query records.
It MUST NOT require a Canonical schema version change, new ingest event type,
new required Span field, or framework object after the adapter boundary.

If later implementation work determines that a finding requires a new
framework-independent observation, it MUST stop and propose a separate
Canonical amendment. It MUST NOT smuggle the field through framework-specific
metadata and call it a stable contract.

### 8.4 Storage compatibility

The comparison and findings read model is derived at query time in P0. No new
SQLite table, migration, persistent finding cache, or SDK spool is required.
Read-only comparison MUST NOT mutate traces, spans, ingest history, idempotency
records, timestamps, or migration state.

If a later optimization adds a cache, it MUST be separately specified and MUST
preserve invalidation, deletion, privacy, and deterministic-output semantics.

### 8.5 Existing detailed data

The v0.3 response MUST provide a read-only endpoint descriptor for the
unchanged v0.2 structural comparison. It MUST NOT embed the complete v0.2
payload in every insight response. The UI MAY fetch that endpoint only when
the user expands detailed evidence. The two requests need not share a database
snapshot; each response MUST truthfully identify its own comparison version
and MUST remain read-only.

## 9. Architecture boundaries

The v0.3 architecture remains:

```text
Framework
  -> Integration Adapter
  -> Canonical Trace Events
  -> Bounded Local Transport
  -> Loopback Collector
  -> SQLite Backend
  -> Query API v1/v2/v3
  -> Inert UI
```

The v0.3 comparison engine belongs after the Query/Repository read boundary.
It MAY use Canonical Trace and Span values and deterministic derived statistics
available through that boundary. It MUST NOT import framework objects, inspect
framework-private state, or re-read raw source values.

The additional LangGraph adapter belongs before Canonical events. The adapter
MUST map public callback observations to existing Canonical types and then use
the shared privacy boundary before transport.

The UI MUST consume `/api/v1`, `/api/v2`, and `/api/v3` only. It MUST NOT open
SQLite, import Python modules, or infer missing evidence from raw captured
content.

The v0.3 implementation MUST preserve:

* framework isolation;
* Collector framework independence;
* UI/API-only access;
* disabled-by-default tracing;
* independently disabled-by-default content capture;
* redaction before the transport queue;
* no deliberate credential persistence;
* no TraceMotive analytics or external telemetry;
* loopback-only Collector and server binding;
* non-fatal tracing failures;
* inert rendering of captured content;
* persistent SQLite behavior and v0.1 deletion semantics.

## 10. First meaningful divergence semantics

### 10.1 Purpose

The first meaningful divergence result identifies the earliest safe place at
which the two observed executions contain an evidence-supported behavioral
divergence. It recommends where to investigate first. It does not assert that
the divergence was important to the task, produced a later result, or caused a
failure.

### 10.2 Eligible P0 signals

Only behavioral observations MAY establish a first meaningful divergence. The
following observations are behavioral candidates:

1. a deterministically resolved Span changes status or gains/loses an error;
2. a uniquely aligned tool Span has a captured input or output difference;
3. a uniquely observed tool Span exists on one side only;
4. a uniquely observed non-tool execution subtree exists on one side only;
5. a repeated sibling group has a deterministic member-count change.

Each eligible signal is only eligible when its evidence and all earlier
coordinates satisfy the rules below.

Known model changes, request-parameter changes, top-level Trace status
changes, and exact latency/token differences remain useful context findings,
but they MUST NOT nominate the first meaningful divergence. When both aligned
observations needed for `model_changed`, `request_parameters_changed`, or
`trace_status_changed` are known and differ, the corresponding finding MAY be
emitted deterministically as context-only diagnostic evidence. A context-only
finding is an observed difference, but it MUST NOT establish an
evidence-supported behavioral divergence, nominate the first meaningful
divergence or an investigation starting point, or imply task relevance,
failure relevance, or causality. Its role is to explain observed context
around a behavioral starting point without pretending that a context change is
the behavioral cause.

### 10.3 Signals that do not qualify by themselves

The following MUST NOT establish a first meaningful divergence by themselves:

* `started_at` or `ended_at` differences;
* a timestamp-only ordering difference;
* a latency or token difference without a later, separately specified policy;
* Canonical `trace_id`, `span_id`, or `parent_span_id` differences;
* framework-native IDs or response IDs;
* source framework/integration version metadata differences;
* arbitrary metadata or attributes not covered by an explicit v0.3 allowlist;
* a JSON inequality in an unavailable or not-captured content field;
* a redacted value difference as a fully confirmed original-value difference;
* a repeated sibling ordinal mismatch;
* a missing tail in an incomplete trace;
* a framework-specific callback event that has no stable Canonical mapping.

### 10.4 Alignment input

The v0.3 engine MUST begin with the v0.2 Simple Structural Alignment v1
result. The following rules remain normative:

* Canonical IDs are execution-local and MUST NOT be cross-run identity;
* framework-native IDs are in-run references only unless a future separate
  contract proves run-to-run stability;
* no nearest-neighbor, timestamp-tolerance, name-similarity, I/O-similarity,
  heuristic, or confidence-based pairing is allowed in the P0 exact layer;
* a repeated same-signature sibling group MUST NOT be paired by ordinal alone;
* ambiguity and unavailable evidence MUST remain localized.

The v0.3 engine MAY classify a deterministic group-level fact without pairing
members. For example, a tool signature with left count `2` and right count
`3` supports a count-change finding, but does not identify which right member
was inserted.

### 10.5 Structural coordinate

Every candidate has a coordinate:

```json
{
  "kind": "span",
  "semantic_path": [
    {"type": "agent", "operation": "agent.run", "name": "support", "ordinal": 0},
    {"type": "tool", "operation": "tool.execute", "name": "search_customer", "ordinal": 0}
  ],
  "group_signature": null
}
```

For a repeated group, the coordinate is:

```json
{
  "kind": "sibling_group",
  "semantic_path": [
    {"type": "agent", "operation": "agent.run", "name": "support", "ordinal": 0}
  ],
  "group_signature": {
    "type": "tool",
    "operation": "tool.execute",
    "name": "search_customer"
  }
}
```

The group coordinate deliberately has no member ordinal.

For a top-level Trace status finding, the coordinate is:

```json
{
  "kind": "trace_summary",
  "semantic_path": [],
  "group_signature": null
}
```

### 10.6 Deterministic coordinate ordering

The phrase “first” means first in this ordering, not first by wall-clock
timestamp and not causal order:

1. the synthetic trace root;
2. immediate child signature groups in Unicode code-point order by
   `(type, operation, name)`;
3. a unique child Span at its structural position;
4. a repeated group at its group coordinate before any member-level detail;
5. descendants after their uniquely resolved parent;
6. a terminal Trace summary coordinate after all Span/group coordinates.

Within a unique group, the v0.2 ordinal is retained for display and deterministic
path identity. It is not an assertion that the Span is the same logical
occurrence across runs when the active rules do not uniquely resolve it.

For equal coordinates, findings are ordered by:

1. coordinate kind;
2. finding type in the fixed enum order in §11.3;
3. JSON Pointer field path in RFC 6901 code-point order;
4. left reference `(started_at, span_id)`;
5. right reference `(started_at, span_id)`;
6. reason code.

The ordering is reproducibility metadata only. API and UI copy MUST NOT call
it causal, temporal, preceding, or responsible.

### 10.7 Meaningful-divergence algorithm

For one comparison read snapshot, the engine MUST:

1. load both Traces and all input Spans under one consistent Repository read
   snapshot;
2. obtain the v0.2 structural alignment result;
3. construct deterministic Span and group coordinates;
4. generate eligible findings and uncertainty records in coordinate order;
5. mark each structural ambiguity, unavailable observation, capture-unavailable
   field, redacted observation, or incomplete lifecycle as a barrier when it
   can hide an earlier evidence-supported behavioral divergence;
6. select the earliest eligible confirmed behavioral finding only when no
   earlier barrier exists;
7. otherwise return an uncertain result and expose the blocking evidence;
8. record the last reliably matched execution point before the selected finding
   or first blocking barrier;
9. attach later same-region and descendant findings as observed evidence, not
   causal edges;
10. return `none` only when no evidence-supported behavioral divergence exists
    and no uncertainty barrier prevents that conclusion.

For determinism, a barrier blocks a global first claim exactly when its
coordinate is at or before the candidate in §10.6 order and its unresolved
observation could hide one of the behavioral signals in §10.2. Structural
ambiguity, missing parents, capture-unavailable or redacted tool values, and
an incomplete lifecycle are blocking barriers when they meet that rule.
Unknown context-only fields are not barriers. A barrier may therefore leave
later branch findings visible while changing the global result to
`uncertain`; it MUST NOT be decided by a confidence score or implementation
intuition.

### 10.8 First-result states

For a successful comparison, `investigation.state` MUST be one of:

* `identified`: a confirmed observation is the earliest eligible finding and
  no earlier barrier exists;
* `uncertain`: a possible finding exists, but capture, redaction, ambiguity,
  incomplete lifecycle, or another barrier prevents a reliable earliest claim;
* `none`: both traces are complete enough for the compared coordinates and no
  behavioral difference was observed. Context-only findings MAY still be
  returned;

Comparison-limit and other request failures return the §13.1 error response;
they do not return a partial success object with an `unavailable`
investigation state.

`identified` MUST NOT be used for a redacted-only content difference, an
ordinal-only difference, a later candidate behind an earlier uncertainty
barrier, or a side-only tail from an incomplete run.

### 10.9 Last reliably matched point

The result MUST include `last_reliably_matched_point`:

```json
{
  "semantic_path": [],
  "left": null,
  "right": null,
  "state": "none",
  "reason": "no_prior_resolved_point"
}
```

When a unique structural Span is safely matched before the first finding, the
result MUST include both left and right references and `state: "matched"`.
When a barrier occurs before any safe point, both references are `null`.
Allowed reasons are `no_prior_resolved_point`, `before_first_finding`, and
`before_uncertainty_barrier`.

This field means “last reliably matched structural observation”; it does not
mean the last causal event.

### 10.10 Descendant evidence

Findings after the selected coordinate MAY be related using:

```json
{
  "finding_id": "finding-0002",
  "relation": "observed_after",
  "relative_to": "finding-0001"
}
```

`observed_after` is based on the structural coordinate order. A descendant
finding MAY be shown as evidence in the same subtree or later execution
region. It MUST NOT be serialized as `caused_by`, `root_cause_of`,
`responsible_for`, or an equivalent claim.

## 11. Deterministic diagnostic findings model

### 11.1 Design rule

Each finding MUST explain itself using structured, sanitized evidence. A
finding MUST NOT be a label attached to an opaque score.

There is no P0 severity field. TraceMotive cannot objectively rank the
severity of arbitrary agent behavior from the current Canonical model. The
investigation summary supplies a deterministic starting point based on
coordinate order and evidence availability, not a fake severity score.

### 11.2 Finding shape

Every finding MUST have this shape:

```json
{
  "finding_id": "finding-0001",
  "type": "tool_output_changed",
  "coordinate": {
    "kind": "span",
    "semantic_path": [],
    "group_signature": null
  },
  "left": {"trace_id": "...", "span_id": "..."},
  "right": {"trace_id": "...", "span_id": "..."},
  "field_path": "/output",
  "scope": "behavioral",
  "observation_state": "confirmed_observation",
  "reason_code": "captured_values_differ",
  "observed": {
    "left": {"state": "captured", "value": {}},
    "right": {"state": "captured", "value": {}}
  },
  "evidence": [],
  "relationships": []
}
```

Rules:

* `finding_id` MUST be assigned after deterministic sort and use
  `finding-0001`, `finding-0002`, and so on;
* `left` or `right` MAY be `null` only when the finding is inherently
  one-sided or trace-level;
* all values MUST be sanitized Canonical values;
* `field_path` MUST be an RFC 6901 JSON Pointer or `null` for a group/status
  finding;
* `scope` MUST be `behavioral` or `context_only`; only `behavioral` findings
  participate in first-meaningful-divergence selection;
* `observation_state` is `confirmed_observation` or `observation_limited`;
* `evidence` MUST contain the exact observations used;
* `relationships` MUST use only the relationship values in §10.10.

The stable P0 `reason_code` registry is:
`error_observed`, `error_resolved`, `captured_values_differ`,
`unique_tool_presence`, `deterministic_group_count_changed`,
`structural_subtree_presence_changed`, `known_model_changed`,
`known_request_parameters_changed`, and `observed_trace_status_changed`.
An implementation MUST NOT invent a free-form reason code for a listed
finding type.

### 11.3 P0 finding types

The fixed P0 finding order is:

1. `new_error`;
2. `resolved_error`;
3. `tool_output_changed`;
4. `tool_input_changed`;
5. `tool_added`;
6. `tool_removed`;
7. `tool_repetition_changed`;
8. `execution_subtree_added`;
9. `execution_subtree_removed`;
10. `model_changed`;
11. `request_parameters_changed`;
12. `trace_status_changed`.

The implementation MUST NOT add a second spelling or synonymous public enum
without revising this specification.

### 11.4 Finding support matrix

| Finding | Safe P0 condition | Not enough evidence |
|---|---|---|
| `new_error` | aligned Span is non-error/absent on left and `status=error` with an error observation on right, or a uniquely added Span is observed error | error inferred only from a missing tail, unavailable parent, or unknown content |
| `resolved_error` | aligned Span is `error` on left and `ok` with no error on right | a missing right Span, incomplete right Trace, or unavailable right evidence |
| `tool_output_changed` | uniquely aligned tool Span; both output CaptureInfo values are captured; sanitized values differ | either output is not captured, original redacted values, or repeated members are unresolved |
| `tool_input_changed` | uniquely aligned tool Span; both input CaptureInfo values are captured; sanitized values differ | same as output, including disabled capture |
| `tool_added` | exactly one uniquely observed tool signature member on right with no left counterpart under a resolvable parent | repeated group count change, incomplete right tail, or ambiguous parent |
| `tool_removed` | exactly one uniquely observed tool signature member on left with no right counterpart under a resolvable parent | repeated group count change, incomplete left tail, or ambiguous parent |
| `tool_repetition_changed` | tool group counts are deterministically known and differ; members remain unpaired | an unavailable or incomplete group count |
| `execution_subtree_added` | a uniquely observed non-tool child/subtree is present only on right under a resolvable parent | ambiguous group, missing parent, or incomplete right tail |
| `execution_subtree_removed` | a uniquely observed non-tool child/subtree is present only on left under a resolvable parent | ambiguous group, missing parent, or incomplete left tail |
| `model_changed` | both known model observations exist on a unique aligned LLM Span and differ; scope is `context_only` | one side is `null`, unavailable, or only provider metadata changed |
| `request_parameters_changed` | both sanitized request-parameter objects are known on a unique aligned LLM Span and differ; scope is `context_only` | one side is absent/unknown or arbitrary metadata changed |
| `trace_status_changed` | observed Trace status values differ; scope is `context_only` and terminal | no valid observed status on one side |

The `context_only` scope is normative. A finding exists does not necessarily
mean that a behavioral divergence exists. In particular, `model_changed`,
`request_parameters_changed`, and `trace_status_changed` MAY report supported
observed differences, but MUST NOT establish an evidence-supported behavioral
divergence, nominate the first meaningful divergence or an investigation
starting point, or imply task relevance, failure relevance, or causality.
For example, a model-only change with otherwise identical supported execution
has an observed difference and MAY have a `model_changed` finding, but has no
behavioral divergence and no investigation starting point.

### 11.5 Error findings

An error finding MUST use the observed Span status and Error fields. A child
Span error MUST NOT be promoted to a Trace error. The finding MAY include a
Trace-level status change as a separate finding if the Trace status also
changed.

`new_error` and `resolved_error` MUST include evidence records for:

* left/right Span status;
* left/right `error.type` when present;
* left/right `error.message` when present;
* CaptureInfo only when content is relevant to a separate content finding.

An error message is sanitized free text. It is not evidence of an unredacted
secret or of a cause.

### 11.6 Content findings

Content findings MUST consult CaptureInfo before comparing values:

* captured on both sides and equal: no finding;
* captured on both sides and unequal: `confirmed_observation`, unless either
  CaptureInfo has `redacted=true`;
* redacted on either side and sanitized values unequal: a finding MAY be
  emitted as `observation_limited` with reason `redacted_observation`, but it
  MUST NOT establish an `identified` first divergence;
* not-captured on either side: no content difference finding; emit an
  uncertainty barrier;
* captured JSON `null` is a known value;
* not-captured JSON `null` is not a known value;
* the comparison layer MUST NOT retrieve raw source values or perform a second
  secret-detection pass.

### 11.7 Repetition and structural-subtree findings

`tool_repetition_changed` reports only a deterministic group fact:

```json
{
  "left_count": 2,
  "right_count": 3,
  "group_signature": {
    "type": "tool",
    "operation": "tool.execute",
    "name": "search_customer"
  }
}
```

It MUST NOT name an inserted or removed member. It MUST NOT call the behavior
retry unless a future Canonical contract explicitly exposes retry semantics.

An execution subtree is a structural child subtree, not a semantic graph
branch or routing decision. `execution_subtree_added` and
`execution_subtree_removed` describe observed structural presence only.

### 11.8 Model and request parameter findings

Model findings use only the Canonical LLM detail fields. `response_id`, source
versions, and framework-native metadata are excluded. A `null` model on one
side is not assumed to mean that the provider used no model; it is an
observation limitation unless both sides expose comparable known values.

Request parameters MUST be the already allowlisted and sanitized Canonical
request-parameter object. The comparison MUST preserve exact numbers and
must not treat a missing key as a provider-default value.

### 11.9 Raw metrics remain detail only

Latency and token aggregates remain available as exact v0.2 trace statistics.
They do not produce v0.3 findings and do not affect first-divergence selection.
No query threshold, default, relative-baseline rule, or regression label is
introduced here. A later specification may define metric policy only after a
separate product decision and workload evidence.

### 11.10 Unsupported proposed examples

The following names are deliberately not P0 findings:

* `retry_pattern_changed` — the current Canonical model has no explicit retry
  event or retry identity contract;
* `latency_regression`, `input_token_regression`, and
  `output_token_regression` — metric policy is intentionally deferred;
* `failure_fingerprint_changed` — no fingerprint contract exists;
* `root_cause_candidate` — causal ranking is out of scope;
* `branch_cause` — structural branch presence is not a causal edge.

The absence of these findings is a correctness decision, not missing polish.

### 11.11 Evidence record

Each evidence item MUST have this shape:

```json
{
  "kind": "field_observation",
  "path": "/details/request_model",
  "left": "model-a",
  "right": "model-b",
  "state": "different",
  "reason": null
}
```

Allowed `kind` values are `field_observation`, `status_observation`,
`group_count`, `side_presence`, and `structural_limitation`. Allowed states
are `same`, `different`, `left_only`, `right_only`, and `unknown`. Evidence values MUST be redacted Canonical
values or `null` where the state says the value is unknown/absent.

### 11.12 Uncertainty records

Uncertainty records MUST have this shape:

```json
{
  "uncertainty_id": "uncertainty-0001",
  "coordinate": {
    "kind": "sibling_group",
    "semantic_path": [],
    "group_signature": {}
  },
  "reason_code": "repeated_sibling_ambiguity",
  "side": "both",
  "blocks_earlier_claim": true,
  "evidence": []
}
```

Allowed `reason_code` values are:

* `repeated_sibling_ambiguity`;
* `missing_parent`;
* `cycle`;
* `invalid_structure`;
* `ambiguous_parent`;
* `capture_unavailable`;
* `redacted_observation`;
* `incomplete_trace`;
* `unsupported_observation`.

`side` MUST be `left`, `right`, or `both`. A comparison limit is not emitted
in a successful response; a limit returns the §13.1 `413` error instead.

Uncertainty IDs are assigned after deterministic sort as
`uncertainty-0001`, `uncertainty-0002`, and so on.

## 12. Evidence summary and investigation context

### 12.1 Summary shape

The v0.3 API MUST return an `investigation` object:

```json
{
  "state": "identified",
  "ordering_basis": "structural_triage_order",
  "starting_point": {
    "kind": "span",
    "semantic_path": [],
    "left": {"trace_id": "...", "span_id": "..."},
    "right": {"trace_id": "...", "span_id": "..."},
    "finding_id": "finding-0001",
    "label": "Inspect tool output change"
  },
  "first_meaningful_divergence": {
    "state": "identified",
    "ordering_basis": "structural_triage_order",
    "finding_id": "finding-0001",
    "reason_code": "captured_values_differ"
  },
  "last_reliably_matched_point": {},
  "evidence_summary": [],
  "blocking_uncertainty_ids": [],
  "limitations": []
}
```

`starting_point` MAY be `null` for `none`. For `uncertain`,
it MAY contain a candidate, but its label MUST say `Possible starting point`
or equivalent and the UI MUST show the blocking uncertainty first.

### 12.2 What the summary may say

The summary MAY state:

* “First meaningful divergence: observed tool output changed.”
* “Investigation starting point: inspect `search_customer` output.”
* “Observed afterward: downstream Trace status changed to error.”
* “Uncertain: an earlier repeated sibling group could not be paired.”
* “No reliable divergence identified from the available observations.”

The summary MUST NOT state:

* “`search_customer` caused the failure.”
* “Root cause is the tool output.”
* “The first error is responsible.”
* “This span is proven to be the culprit.”

### 12.3 Evidence-summary relationships

The summary is a deterministic list of findings and uncertainties ordered by
structural coordinate. Each relation MUST be one of:

* `same_structural_region`;
* `descendant_evidence`;
* `observed_after`;
* `terminal_summary`;
* `blocked_by_uncertainty`.

The summary is explanatory presentation data. It is not a graph of causes,
and the field name deliberately avoids implying a causal chain.

### 12.4 Example

```text
Investigation starting point:
  search_customer — observed output changed

Observed around and afterward:
  structural subtree present only on the right
  repeated lookup group count changed from 1 to 3
  right Trace status changed from ok to error

Uncertainty:
  repeated members were not paired; no individual inserted call is asserted
```

The example is valid only if each listed observation is supported by the
corresponding Canonical evidence and the first result is not blocked by an
earlier unavailable coordinate.

## 13. Comparison API evolution

### 13.1 Endpoint

The additive v0.3 endpoint is:

```text
GET /api/v3/compare/{left_trace_id}/{right_trace_id}
```

The endpoint MUST validate IDs, reject equal IDs with `400`, return `404` when
either trace is absent, return `413` for configured comparison limits, and
return a safe generic `500` for internal failure. It MUST use one consistent
Repository read snapshot for both traces and all spans.

Error responses MUST use the same generic shape as v0.2:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "invalid request"
  }
}
```

The v0.3 status/code/message mapping is:

| Status | Code | Message |
|---:|---|---|
| 400 | `invalid_request` | `invalid request` |
| 404 | `not_found` | `not found` |
| 413 | `comparison_too_large` | `comparison too large` |
| 500 | `internal_error` | `internal error` |

Responses MUST NOT expose database paths, stack traces, exception classes,
framework objects, raw exception text, or unsanitized values.

### 13.2 Threshold policy

There are no v0.3 threshold query parameters. Exact latency and token
aggregates remain available in the existing v0.2 detail endpoint, but they do
not create v0.3 findings. A later metric policy requires a separate
specification and compatibility review.

### 13.3 Successful response shape

The successful v0.3 response MUST have this top-level shape:

```json
{
  "comparison_version": "0.3",
  "left_trace": {},
  "right_trace": {},
  "summary": {},
  "investigation": {},
  "findings": [],
  "uncertainties": [],
  "detail_endpoint": {
    "method": "GET",
    "path": "/api/v2/compare/{left_trace_id}/{right_trace_id}",
    "comparison_version": "0.2"
  }
}
```

`detail_endpoint` MUST point to the unchanged v0.2 comparison route for the
same trace IDs. It is a navigation descriptor, not an assertion that a later
request will see the same database snapshot. The v0.2 response MUST retain
its `exact_match`, `left_only`, `right_only`, `ambiguous_group`, and
`unavailable` semantics.

### 13.4 Summary shape

The v0.3 `summary` MUST contain:

```json
{
  "alignment": {
    "matched_spans": 0,
    "left_only_spans": 0,
    "right_only_spans": 0,
    "ambiguous_groups": 0,
    "unavailable_spans": 0
  },
  "finding_count": 0,
  "uncertainty_count": 0,
  "trace_fields": []
}
```

The alignment object MUST equal the counts produced by the v0.2 alignment
function for the same v3 read snapshot; a later separately fetched detail
response may reflect a newer database state.
`finding_count` MUST equal `findings.length`. `uncertainty_count` MUST equal
`uncertainties.length`. Trace field values retain v0.2 exact-number and
unknown semantics.

### 13.5 Limits

The initial v0.3 comparison limits are the v0.2 limits:

* at most 10,000 persisted Spans per input Trace;
* at most 4,096 emitted difference/finding/uncertainty records as defined by
  the implementation's pre-serialization limit accounting;
* at most 4 MiB serialized response body.

The endpoint MUST return `413` without a partial response when a limit is
exceeded. The endpoint MUST NOT claim a first divergence from truncated data.

V03-60 MAY recommend a later limit change, but a change requires a separate
compatibility decision and MUST NOT silently alter `/api/v2`.

### 13.6 Read-only behavior

The v0.3 endpoint MUST NOT write findings, update trace timestamps, modify
CaptureInfo, add ingest events, alter SQLite migration state, or delete data.

### 13.7 Determinism

For identical persisted Canonical inputs, the serialized v0.3 response MUST be
byte-for-byte deterministic, including finding IDs, uncertainty IDs, field
order, object-key order, and exact numbers. A separately fetched v0.2 detail
response remains independently deterministic under its existing contract.

## 14. Insight-first comparison UI

### 14.1 P0 hierarchy

The comparison page MUST present information in this order:

1. **What changed?** — compact observed finding summary;
2. **Where did execution first meaningfully diverge?** — state and coordinate;
3. **What evidence changed around it?** — findings and evidence values;
4. **What should I inspect first?** — a link to the Trace Detail/Span
   Inspector or the repeated group detail;
5. **What is uncertain?** — barriers and limitations before the raw detail;
6. **Detailed structural comparison** — the current v0.2 data below.

The first screen MUST answer in plain language: whether an observed behavioral
difference exists, where to inspect first, what changed there, what was
observed afterward, and what remains unknown. JSON Pointers, reason codes,
coordinates, protocol versions, and Canonical terminology MUST be collapsed
under an evidence/details affordance; they are not primary user copy.

### 14.2 State labels

The UI MUST visibly distinguish:

* `confirmed observation`;
* `observed difference`;
* `possible starting point`;
* `ambiguous`;
* `unavailable`;
* `capture unavailable`;
* `redacted observation`;
* `incomplete trace`;
* `no reliable divergence identified`.

An API `404`, `413`, or `500` is rendered as a separate comparison error;
`unavailable` is reserved for localized v0.2 structural records and is not a
successful v3 investigation state.

Color alone MUST NOT carry these distinctions. Text, accessible labels, and
stable structure are required.

### 14.3 Uncertainty behavior

If `investigation.state=uncertain`, the page MUST display the uncertainty
before any candidate starting point. It MUST NOT use a confident highlight,
arrow, badge, or heading that implies the candidate is proven.

The UI MUST state that “first” means structural triage order, not runtime
chronology or causality.

When a supported starting point is shown, the UI MUST make the following
meaning explicit, using this wording or an equally strict translation:

> TraceMotive observed this difference and selected it as the first supported
> place to investigate. TraceMotive does not know whether the difference
> caused the later failure.

Context-only findings MUST be labeled as observed context. The UI MUST NOT
present `model_changed`, `request_parameters_changed`, or
`trace_status_changed` as a behavioral divergence or an investigation starting
point.

An ambiguous repeated group MUST show its signature, left/right counts,
member references where available, and the statement that individual members
were not paired. It MUST NOT show an ordinal-only member as an exact pair.

Capture-disabled and redacted values MUST use the existing CaptureInfo-aware
semantics. A captured JSON `null` MUST remain distinct from not-captured
`null`.

### 14.4 Detailed v0.2 comparison

The v0.2 comparison MUST be loaded lazily from `detail_endpoint` only after
the user requests detailed evidence. The initial v0.3 response and initial
render MUST not carry or render the full v0.2 span list. When loaded, the
current v0.2 comparison remains below the insight section, with:

* all results;
* `Changed only` filtering;
* exact/left-only/right-only/ambiguous/unavailable records;
* side-by-side observed values;
* exact number preservation;
* inert untrusted content rendering.

The v0.3 page MUST NOT remove the detailed route or require a user to accept
the insight summary as a substitute for evidence. If the detail request fails,
the insight result remains visible and the UI shows a local, non-causal error
state rather than silently treating detail as absent.

### 14.5 Navigation

For a unique Span finding, the UI SHOULD link to the existing Span Inspector
using the `(trace_id, span_id)` reference. For a group finding, it SHOULD link
to the comparison detail group and show both sides' member references. No link
label may say “root cause” or “culprit.”

### 14.6 UI safety

Captured values remain untrusted data. The UI MUST NOT execute HTML, script,
event handlers, CSS injection, or arbitrary code from captured input/output,
metadata, attributes, errors, or finding evidence. API errors are rendered
from safe local labels, not raw response bodies.

## 15. Additional framework adapter: LangGraph

### 15.1 Admission target

The single additional native framework integration targeted for v0.3 is
LangGraph. The initial validation candidate is one exact package version:

```text
langgraph==1.2.9
Python >=3.10
```

This is a validation target, not a support claim. V03-40 and V03-41 MUST
admit only exact versions with real public-API and real-run evidence. A later
release MAY admit more versions, but each version must be named in release
evidence; a broad `1.2.x` claim is not implied by testing one patch.

The adapter MUST be optional. The core package MUST remain importable without
LangGraph, LangChain, or LangGraph-related extras.

### 15.2 Integration entry point

The proposed public adapter entry point is:

```python
from tracemotive.integrations.langgraph import LangGraphTracingCallback

callback = LangGraphTracingCallback()
result = graph.invoke(
    input_value,
    config={"callbacks": [callback], "run_name": "support_graph"},
)
tracemotive.flush()
```

The callback MUST use documented public callback/configuration APIs. It MUST
not require LangSmith, a LangGraph server, a cloud account, or a remote
collector. The final signature may be adjusted only before V03-40 closes and
must then be recorded in the compatibility documentation and tests.

### 15.3 Candidate public observations

The adapter MAY support the following observations only when the tested public
callback path actually emits them. The table is an admission checklist, not a
claim that every graph or plain Python node produces every event:

| Public callback observation | Canonical mapping |
|---|---|
| root graph/chain start and end/error | one Canonical Trace lifecycle |
| graph/node chain start and end/error | `custom` or `agent` Span with `langgraph.node` operation, when emitted |
| chat-model/LLM start and end/error | `llm` Span with known model/usage fields when available |
| tool start and end/error | `tool` Span with tool name and input/output when available |
| retriever start and end/error, only if reliably exposed | `retrieval` Span with existing RetrievalDetails |
| public `run_id`/`parent_run_id` | in-run native source and parent mapping only |
| public tags/metadata | sanitized Canonical metadata/attributes only after allowlist review |

The adapter MUST not persist a whole callback object or framework runtime
object. It MUST use the shared CaptureInfo and pre-transport privacy boundary.

### 15.4 Parent and identity rules

Native callback IDs are used only to maintain an in-process mapping during one
observed invocation. They MUST NOT be used as v0.3 cross-run alignment
identity. Canonical `(trace_id, span_id)` values remain execution-local.

When a public callback has no parent ID, the adapter MAY create a root Span
only when the event is a documented root event. It MUST NOT invent a parent
from callback arrival order. Missing or contradictory parent evidence MUST be
represented as a local unavailable/uncertain observation.

### 15.5 Content and privacy boundary

* TraceMotive and content capture remain independently disabled by default;
* callback inputs/outputs are captured only when the existing configuration
  enables capture and the public callback supplies the value;
* capture-disabled callbacks MUST not be probed for content;
* normalization, redaction, size limits, and CaptureInfo precedence remain the
  Frozen v0.1 behavior;
* known keys, authorization values, and framework credentials MUST not be
  copied into metadata, attributes, errors, or logs;
* callback errors and serialization failures MUST not fail graph execution.

### 15.6 Unsupported behavior

The v0.3 LangGraph adapter MUST NOT claim support for:

* LangGraph server/cloud deployment;
* LangSmith export or remote telemetry;
* cross-invocation checkpoint causality;
* replay or resume causality across separate `invoke` calls;
* full graph topology as an observed execution branch when no callback event
  proves that the branch ran;
* token/chunk streaming persistence;
* retry semantics unless a future Canonical retry contract is added;
* private runtime objects or undocumented callback fields;
* automatic mapping of arbitrary graph state to captured content.

### 15.7 Real integration requirements

V03-41 MUST run a real public LangGraph application through:

```text
LangGraph -> adapter -> Canonical -> local transport -> loopback Collector
-> SQLite -> Query API -> v0.3 comparison/UI
```

The example MUST include a graph node, an LLM or deterministic model stub,
one tool, a branch or conditional path, and an error variant. It MUST run
without a paid model API by default and MUST have a separate optional real
provider smoke only if documented.

## 16. Demo and first-value onboarding

### 16.1 Command

The proposed local workflow is:

```text
tracemotive serve [--port PORT] [--db PATH]
tracemotive demo [--endpoint ENDPOINT]
```

Rules:

* `serve` owns server startup, port selection, and database selection using
  its existing contract;
* `demo` is a seed-and-link command and MUST NOT start a second server or
  choose a database;
* the default demo endpoint is `http://127.0.0.1:8765`;
* `--endpoint` MUST be loopback-only and MUST fail explicitly for a remote
  host;
* no API key is required;
* no model-provider request is made;
* no repository clone is required;
* Node.js/npm is not required at runtime;
* no external TraceMotive telemetry is sent;
* the server remains loopback-only and has no remote-binding option;
* an unavailable endpoint fails explicitly and does not fall back to another
  port, database, host, or network service;
* the command prints the local trace URL and comparison URL after seeding;
* Ctrl+C remains the responsibility of the separately running local server.

The demo MUST seed through a public, sanitized local path that exercises the
comparison read model. It MUST NOT bypass privacy or the Collector solely to
make the demo easier. The documented first-value path is therefore
`install -> serve -> demo -> open comparison`, with no hidden process or
persistent-database ownership.

### 16.2 Deterministic demo traces

The default pair MUST contain at least:

* a working Trace with an Agent/root observation, an LLM or planning Span, a
  `search_customer` tool Span, and a terminal successful Span/Trace;
* a failing Trace with the same resolvable structure through the tool, a
  changed captured tool output, and a downstream observed error;
* a later structural difference or repeated group that demonstrates localized
  ambiguity without falsely pairing members;
* a comparison showing an investigation starting point, evidence afterward,
  and uncertainty where applicable.

All values MUST be deterministic, non-sensitive, and local. The demo MUST
include no real credential-shaped value that needs to be persisted.

### 16.3 Onboarding acceptance

On the reference release environment, the measured path from a fresh wheel
install to a visible comparison MUST be at most 120 seconds in the V03-90
release smoke. The timing report MUST separate package installation time,
server startup, trace seeding, query/comparison time, and human browser
navigation. The 120-second gate is a test target, not a universal product
SLA.

## 17. Privacy and security

All relevant v0.1 and v0.2 invariants remain mandatory.

### 17.1 Transport and persistence

* TraceMotive is disabled by default;
* content capture is independently disabled by default;
* redaction occurs before a serialized event enters the transport queue;
* the queue retains serialized sanitized Canonical bytes, not raw framework
  objects;
* the Collector persists sanitized Canonical data only;
* known API keys and credentials MUST NOT be intentionally persisted;
* no persistent SDK spool is added;
* SQLite journal/WAL/SHM sidecars remain in scope for privacy inspection;
* comparison findings and the lazy detail endpoint expose only sanitized
  Canonical observations and deterministic derived values;
* the comparison engine does not re-read source values.

### 17.2 Network

* normal Collector and `tracemotive serve` binding remains loopback-only;
* v0.3 adds no remote collector or cloud behavior;
* the demo makes no external model or TraceMotive request;
* the LangGraph adapter makes no LangSmith or hosted service request;
* no analytics or usage collection is added.

### 17.3 Untrusted content

Captured input/output, errors, metadata, attributes, and finding evidence are
untrusted data. The frontend MUST render them inertly. Comparison values MUST
remain bounded by existing Canonical capture and response-size limits.

### 17.4 Failure isolation

Adapter, comparison, transport, Collector, persistence, and UI failures MUST
not turn tracing into an Agent execution failure. A comparison request may
fail safely with a generic HTTP error; it MUST not mutate the runs.

## 18. Performance and scale validation

### 18.1 Purpose

Core v0.3 requires a basic performance-regression check against v0.2 on the
deterministic demo pair and at least one representative persisted comparison
within the existing limits. The check MUST record comparison time, response
size, and whether the v0.3 path introduces a material regression.

V03-60 is conditional P1 workload characterization. It validates broader
realistic local behavior, does not create a generic observability performance
promise, and does not replace correctness gates. It MAY move to v0.3.1 if it
delays the Core debugging workflow.

### 18.2 Reference environment

The release report MUST record the actual environment. The initial gate uses:

* Windows 11 or the repository's supported CI Windows environment;
* Python 3.12;
* four logical CPU cores or more;
* 8 GiB RAM or more;
* local SSD storage;
* Node.js/npm absent from the installed-runtime process environment;
* no external model or network service.

If the actual environment differs, the report MUST state the difference rather
than silently comparing results.

### 18.3 Workload matrix

The benchmark MUST include deterministic sanitized workloads with:

* 1,000 spans per trace;
* 10,000 spans per trace;
* deep trees at depths 32 and 128;
* wide fan-out of at least 100 children;
* repeated same-signature siblings at counts 2, 10, and 100;
* parallel-looking branches with deterministic persisted timestamps;
* long-running/incomplete traces;
* large captured values near the Canonical 256 KiB per-field limit;
* queue pressure and dropped telemetry;
* Collector restart with file-backed SQLite;
* comparison against a realistic persisted database containing at least
  100 traces;
* v0.3 demo traces through the installed wheel.

At least one workload MUST pass through public SDK/Collector paths. Synthetic
Canonical fixtures MAY supplement it for extreme scale, but MUST NOT be the
only evidence for full-stack behavior.

### 18.4 Release-gate ceilings

The proposal does not invent absolute latency or memory promises. Before
running the final comparison, V03-60 MUST publish workload-specific ceilings
derived from a measured v0.2 baseline and the supported response/trace-size
contract. V03-90 MUST either meet those ceilings or narrow the supported
workload and record the release blocker. The report MUST include at least:

| Measurement | Required evidence |
|---|---|
| v0.2 versus v0.3 comparison p50/p95 | per workload, with sample count and baseline |
| v0.2 versus v0.3 detail query p50/p95 | per workload, with response size |
| peak process RSS | per workload and process phase |
| safe limit rejection | deterministic `413` behavior without partial findings |

The report MUST state the exact ceiling and why it is appropriate before
results are used for release approval. It MUST NOT turn a convenient timeout
or an arbitrary round number into a product promise.

The comparison engine MUST avoid N+1 database queries for a pair, use bounded
memory proportional to the loaded pair, and make the result-size accounting
explicit before serialization. After bulk load, alignment and finding work
MUST be O(n log n) or better in the total loaded Span count; it MUST NOT use an
all-pairs O(n²) cross-run comparison. A 10,000-span response may safely return
`413` when the defined output limit is exceeded. The benchmark MUST separately
record whether the rejection is deterministic, bounded, and privacy-safe.

### 18.5 Other measurements

The report MUST measure and retain:

* startup time;

## 19. Adversarial evaluation corpus

### 19.1 Corpus purpose

V03-10 MUST define a versioned, deterministic corpus before production
implementation of the divergence engine. The corpus is the primary defense
against false confidence.

Each pair MUST record an external expected-safe result. The oracle MAY use
human-authored logical labels unavailable to production comparison code.

### 19.2 Required scenarios

| Scenario | Required safe behavior |
|---|---|
| near-identical runs | no timestamp-only divergence; stable output |
| inserted repeated tool call | group count finding or uncertainty; no incorrect exact member pair |
| removed repeated tool call | group count finding or uncertainty; no incorrect exact member pair |
| reordered repeated calls | no ordinal-only first divergence; localized ambiguity |
| changed tool output | exact aligned output finding only when both captures are known |
| changed tool input | exact aligned input finding only when both captures are known |
| changed routing subtree | unique structural-subtree finding when resolvable; otherwise uncertainty |
| new downstream error | `new_error` at the observed error Span; no causal claim |
| error before later divergence | earlier error finding wins structural coordinate order |
| timing-only variation | exact metric detail only; no v0.3 finding |
| token-only variation | exact metric detail only; no v0.3 finding; exact zero preserved |
| missing parent | local unavailable barrier; unrelated branches remain usable |
| duplicate structural siblings | localized ambiguity; no guessed pair |
| deep repeated subtrees | descendants remain ambiguous/unavailable as applicable |
| partial/incomplete trace | missing tail is not called removed behavior |
| capture disabled on one side | content comparison unknown; barrier is visible |
| redaction on one side | sanitized difference is observation-limited; no confirmed original-value claim |
| both runs failing differently | separate observed findings; no cause assignment |
| identical failures | no evidence-supported behavioral divergence from identical observed failure evidence |
| one run terminating early | incomplete-trace uncertainty; no confident removed-tail finding |
| framework metadata-only difference | no behavioral finding |
| model change with both known models | observed difference and deterministic context-only `model_changed` at uniquely aligned LLM Span; no evidence-supported behavioral divergence or investigation starting point |
| request parameters with one unknown side | no confirmed parameter finding; uncertainty is explicit |
| request parameter change with both known parameters | observed difference and deterministic context-only `request_parameters_changed` at uniquely aligned LLM Span; no evidence-supported behavioral divergence or investigation starting point |
| trace status change with both observed statuses | observed difference and deterministic context-only `trace_status_changed`; no evidence-supported behavioral divergence or investigation starting point |
| latency/token-only variation | exact metrics remain detail; no v0.3 finding or first-divergence claim |

### 19.3 Corpus evidence boundary

The corpus MUST include:

* a public-path or sanitized real-trace-derived set for supported integrations;
* deterministic Canonical variants with execution-local and native IDs
  independently regenerated;
* no production access to the oracle labels;
* no secret or raw credential values;
* a repeatability check across fresh processes;
* a full-stack subset through HTTP Collector, SQLite, Query API, and UI.

### 19.4 False-confidence metric

The primary release metric is:

```text
false confident first-meaningful-divergence = 0
```

on every approved corpus pair.

A false confident result is any result that:

* reports `investigation.state=identified` at a coordinate later than a hidden
  evidence-supported behavioral divergence behind an uncertainty barrier;
* reports an ordinal-only repeated member as an exact logical identity;
* reports a content difference as confirmed when CaptureInfo is unavailable;
* reports a redacted original-value difference as confirmed;
* labels an incomplete tail as confidently removed behavior;
* claims a cause, root cause, causal proof, responsibility, or blame;
* changes across repeated executions of the same persisted input without an
  input change.

Any false confident result blocks the v0.3 release. The engine MUST return
uncertainty rather than guess.

### 19.5 Mutation checks

The corpus tests SHOULD include mutants that:

* replace group identity with ordinal identity;
* treat missing content as equal to `null`;
* treat redacted sanitized values as original values;
* use timestamps as first-divergence order;
* ignore an earlier ambiguity barrier;
* promote a child error to Trace status;
* convert unknown tokens to zero;
* classify a missing incomplete tail as removed;
* use framework/native IDs across runs;
* call a changed output a root cause.

The release gate is not closed by tests that pass only the unmutated
implementation.

## 20. Error and uncertainty semantics

### 20.1 API errors

API errors use §13.1 generic status/code/message values. No raw backend,
framework, or exception details may be returned.

### 20.2 Local uncertainties

An uncertainty is local whenever safe. One missing parent, ambiguous group, or
capture-unavailable field MUST NOT make unrelated branches disappear. It MAY
block a global “first” claim for later coordinates when it could hide an
earlier divergence.

### 20.3 Incomplete traces

A Trace with `status=unset` or missing terminal observation is incomplete for
first-divergence purposes. Observed spans before the incomplete boundary remain
usable. Absent spans after the boundary MUST NOT be treated as removed
behavior. A later explicitly observed error may still be a finding if its
coordinate is safely known and no earlier barrier blocks the claim.

### 20.4 Redaction and capture

Redaction provenance is part of the evidence state. It is not a reason to
discard the entire comparison. A redacted field can be displayed as a
sanitized observed difference with `observation_limited`; it cannot support a
claim about the original secret-bearing value.

### 20.5 No-confidence-score rule

v0.3 MUST NOT emit a probability, percentage confidence, machine-learned
score, or severity number. The finite state and reason-code model is the
contract for uncertainty.

## 21. MUST / MUST NOT requirements

### 21.1 MUST

v0.3 MUST:

* preserve v0.1 and v0.2 compatibility boundaries;
* use a single consistent read snapshot per comparison;
* keep `/api/v2` available and semantically unchanged;

* modify `spec/v0.1-frozen-spec.md` as part of v0.3 work;
* change package versions in V03-00;

* add a Canonical field solely to satisfy a finding name;
* inspect framework objects in the comparison engine;
* use timestamps as causal order;
* claim root cause or causal proof;
* guess through ambiguity, unavailable capture, redaction, or incomplete
  traces;
* call a repeated ordinal match exact logical identity;
* silently fall back to another database, port, host, or network service;
* add cloud, remote, analytics, authentication, or publication behavior.

## 24. Release gate

The Core v0.3 release candidate is ready only when all of the following are
true:

1. the Frozen v0.1 specification is unchanged;
2. Canonical schema remains `0.1`, ingest remains protocol `1`, and `/api/v1`
   behavior remains compatible;
3. `/api/v2` remains available with v0.2 semantics;
4. `/api/v3` is deterministic, read-only, bounded, and privacy-safe;
5. first meaningful divergence never overclaims past an ambiguity, capture,
   redaction, structural, or incomplete-trace barrier;
6. zero false confident first-divergence results occur on the approved corpus;
7. no finding or UI label claims root cause, causal proof, or responsibility;
8. exact numbers, zero, null, CaptureInfo, and redaction provenance survive
   API/UI/persistence paths;
9. basic performance regression is recorded against the v0.2 baseline;
10. the demo meets the measured first-value gate without API key, model,
    repository clone, Node/npm, or external TraceMotive network traffic;
11. safe limit rejection is recorded; broader scale ceilings are conditional
    P1 evidence;
12. loopback-only, no-telemetry, untrusted-content, non-fatal tracing, and
    sidecar privacy checks pass;
13. the installed wheel works outside the checkout without Node/npm;
14. all existing relevant tests and Core v0.3 tests pass.

V03-40, V03-41, V03-60, and V03-70 are conditional P1 work. They MAY be
released with Core v0.3 when their evidence is complete, but they MUST NOT
block Core approval. If LangGraph validation is technically risky or
destabilizing, it moves to v0.3.1. Broader workload characterization may also
move to v0.3.1 when it delays the Core debugging workflow.

If any condition fails, the verdict is not release-ready. The remedy is to
narrow the contract, fix the implementation, or defer the capability; it is
not to soften the evidence language.

## 25. Deferred work

The following remains outside v0.3 unless a later specification explicitly
defines it:

* causal evidence graphs;
* root-cause analysis;
* intervention-backed hypotheses;
* replay and execution forking;
* automatic regression generation;
* cross-run native identity guarantees;
* retry semantics and retry-specific findings;
* thresholded latency/token findings and metric-regression policy;
* streamed token/chunk capture;
* hosted or distributed deployment;
* multi-user access control;
* broad framework support;
* model recommendation or automatic parameter tuning;
* learned similarity or probabilistic alignment;
* arbitrary secret detection guarantees;
* persistent finding caches and server-side background analysis;
* general monitoring dashboards and alerting.

The v0.3 product is complete when it is exceptionally good at the narrower
workflow of comparing a good run with a bad run and identifying the safest
place to investigate first.
